# 実装前の命名レビュー

ユーザーの明示的な要求により、通常のcc-sdd承認に追加して命名レビューを行う。

レビュー担当の選択・起動・記録と、レビューの回数は[共通引継ぎ手順](../../steering/agent-handoff.md)が正本（命名は、要求・設計・tasksと同じ1回の仕様のレビューで受ける）。自己レビューやinline/offで代替しない。過去のレビュー記録は保持する。

1. specごとに`naming.md`を作り、revisionを付ける。
2. ファイル・型・関数・引数・公開フィールド・永続する状態変数を列挙する。testは、module直下の名前（test module、helper関数、定数、importの別名）だけを列挙し、test関数の名前と、test関数の中の局所名・引数は対象外とする（2026-10-09ユーザー決定。範囲の正本は共通引継ぎ手順）。
3. 各項目の役割、入出力/型、単位、更新する状態、似た名前との違いを説明する。
4. 独立レビューを依頼し、主担当が有用な指摘を反映した後に、worktreeでの実装を開始する（命名表を作るためのリポジトリ外の下書きは可。条件は共通引継ぎ手順）。
5. レビューと指摘の採否・理由を保存し、`approvals.naming.approved`と`approved_revision`を更新する。承認元はユーザーが委任した命名レビューとして記録する。
6. 名前・役割・境界を変えた場合はrevisionを増やして承認を解除する。

`-y`、`--auto`、レビューなしの自己判断は命名承認を代替しない。全指摘の採用は必須ではなく、採否は主担当が根拠に基づいて決める。
未承認の新しいsourceの名前を実装中に導入する必要が出た場合は、命名表へ足してrevisionを上げ、実装のレビューでまとめて確認を受ける（公開する関数・class・moduleの名前を足す・変える場合は、先に命名の再レビューを受ける）。

名前は短さより、意味の明確さ・他の概念と区別できること・実態との一致を優先する。
必要なら4語・5語以上を使い、既に明確な名前を無目的に長くしない。
個別の名前だけが承認された場合は`approvals.naming.approved_identifiers`と確認記録へ保存し、
一覧全体の`approved`は変更しない。承認済みの名前でも役割を変更する場合は再確認する。
