# 実装前の命名レビュー

ユーザーの明示的な要求により、通常のcc-sdd承認に追加して命名レビューを行う。

2026-10-07の訂正指示により、担当ツールを問わずGPT-6 Lunaを優先し、利用不能時はSonnetの独立レビューを使用する。
各段階の承認ゲートと指摘の採否・理由の記録は共通。
実際の担当モデルと代替時のLuna利用不能理由を記録し、過去のレビュー記録は保持する。自己レビューやinline/offで代替しない。

1. specごとに`naming.md`を作り、revisionを付ける。
2. ファイル・型・関数・引数・公開フィールド・永続する状態変数を列挙する。
3. 各項目の役割、入出力/型、単位、更新する状態、似た名前との違いを説明する。
4. GPT-6 Luna（利用不能時はSonnet）へ独立レビューを依頼し、主担当が有用な指摘を反映した後に実装を開始する。
5. レビューと指摘の採否・理由を保存し、`approvals.naming.approved`と`approved_revision`を更新する。承認元はユーザーが委任した命名レビューとして記録する。
6. 名前・役割・境界を変えた場合はrevisionを増やして承認を解除する。

`-y`、`--auto`、レビューなしの自己判断は命名承認を代替しない。全指摘の採用は必須ではなく、採否は主担当が根拠に基づいて決める。
要求・設計・taskの承認も省略しない。これらもGPT-6 Luna（利用不能時はSonnet）の独立レビューと主担当の有用な指摘反映によって承認する。
小さな一時変数は担当task開始前の追加表へまとめる。命名表を全実装の巨大な事前台帳にしない。
未承認の新しい名前を実装中に導入する必要が出た場合は、その追加表をレビューへ戻す。

名前は短さより、意味の明確さ・他の概念と区別できること・実態との一致を優先する。
必要なら4語・5語以上を使い、既に明確な名前を無目的に長くしない。
個別の名前だけが承認された場合は`approvals.naming.approved_identifiers`と確認記録へ保存し、
一覧全体の`approved`は変更しない。承認済みの名前でも役割を変更する場合は再確認する。
