# Requirements Document

## Project Description (Input)

誰の問題か: FedSDAとFedDriftの比較実験コードをリファクタリングしている研究者（主担当と、後で読む人）。

現在の状況: サーバは、登録・集約・配布・集約後の再較正まで行える。旧の最終構成のサーバは、新規モデルが登録されたラウンドで、集約と配布の間に、グローバルモデルどうしをclientの手元の標本で評価し（クロス評価）、その結果でクラスタリングと統合を行う。新には、クロス評価も、クラスタリングと統合もない。

変えたいこと: クロス評価（clientでの評価と、サーバでの集計・通信量・診断の記録）を、旧と同じ順序・数値・乱数の消費で行う。クラスタリングと統合は、次のspecで扱う（調査の結果、2つに分けた）。

調査で確かめたこと（固定旧748c3aa。最終構成は、判定`class_functional_confidence`、対の診断の収集あり、Cachedなし、非劣性の検証なし）:

- サーバ（`servers/clustering.py`の`_cross_evaluate`）: 最初に、各clientの「保有するモデルID」（評価標本・学習データ・保有モデル・現行モデルのIDの和集合）から、モデルIDごとの保有clientの列（clientの順）を作る。評価する側のモデル`i`（外側）と、評価の対象のモデル`j`（内側）の全部の組を、渡されたIDの順に回る。`j`を保有するclientが上限（`CROSS_EVAL_MAX_CLIENTS`）を超えたら、無作為に上限の数を抜き出す。下りと上りの軽量メッセージを、対象のclientの数ずつ足す。モデル`i`のパラメータを送った通信量を足す。`i`と`j`が違えば、各clientに、損失の統計と、正誤の比較（クラス別を含む）を求め、同じなら、損失の統計だけを求める。組ごとに、件数・損失の和・損失の2乗和を、clientの順に足し合わせる。
- 通信量（`servers/shared_backbone.py` 32〜52行）: 1回のクロス評価の中で、共有部は、clientごとに最初の1回だけ（そのときのモデル`i`の共有部）数え、概念固有部は、（モデル`i`、client）ごとに最初の1回だけ、モデル転送数1とともに数える。
- 正誤の比較の集計（同`_record_functional_pair_stats`）: モデルの対を（小さいID、大きいID）の向きにそろえ、評価した標本数と、片方だけが正解した数を、全体とクラス別に足す。
- 診断の記録: 正誤の比較がある評価の記録（評価する側、対象、件数、4つの正誤の数、クラス別）、全評価の記録（ラウンド、client、評価する側、対象、件数、和、2乗和、4つの正誤の数。比較がなければ−1）、クラス別の記録。
- client（`clients/base.py` 476〜636行）: 評価に使う標本は、対象のモデルの評価標本が6件以上あればそれ、なければ、対象が現行モデルで、その学習データが11件以上あればそれ、どちらでもなければ空。上限（`EVAL_MAX_SAMPLES`）を超えたら、無作為に上限の数を抜き出す。標本が5件未満なら、件数0を返す（正誤の比較では、対象のモデルを保有していない場合も）。そうでなければ、新しいモデルを作って（torchの乱数を消費）、渡されたパラメータの値にし、標本ごとの有界損失の、件数・和・2乗和（float32の配列の和）を返す。正誤の比較では、同じ標本で、渡されたモデルの予測と、自分が保有する対象のモデルの予測を、観測ラベルと比べ、「渡されたモデルだけ正解・対象だけ正解・両方正解・両方不正解」を、全体と、標本に現れたクラス（昇順）ごとに数える。
- clientの状態は、評価で変わらない（乱数だけが進む）。計算量と所要時間の記録は、移植しない。

## Introduction

研究者が、グローバルモデルのクロス評価を、旧と同じ結果になる呼出しで行えるようにする。結果（損失の統計の表と、対ごとの正誤の集計）は、次のspecのクラスタリングの入力になる。

## Boundary Context

- **In scope**: client 1つの、渡されたモデルの評価（標本の選択、損失の統計、保有する対象のモデルとの正誤の比較）。clientの「クロス評価で保有とみなすモデルID」。サーバのクロス評価（保有clientの列、組の走査、clientの抜出し、通信量、集計、診断の記録）。診断の記録のowner。
- **Out of scope**: 距離と判定の計算、linkage、統合、ID対応、ラウンドへの接続（次のspec）。Cached方式、非劣性の検証（損失差の統計）。計算量と所要時間の記録。記録の保存。
- **Adjacent expectations**: 標本ごとの有界損失と、予測クラスの計算は、移植済みの部品をそのまま使う。

## Requirements

### Requirement 1: clientでの評価

**Objective:** As a 研究者, I want clientが、渡されたモデルを、旧と同じ標本と式で評価してほしい, so that クラスタリングの入力が旧と同じになる

#### Acceptance Criteria

1. When 評価を求められたとき, the Run Client shall 対象のモデルの評価標本が6件以上あればそれを、なければ、対象が現在の学習帰属のモデルで、その学習データが11件以上あればそれを使い、どちらでもなければ標本なしとする。標本が上限を超えたら、借りた乱数生成器で、上限の件数を無作為に抜き出す。
2. When 標本が5件未満のとき、または正誤の比較を求められて対象のモデルを保有していないとき, the Run Client shall 件数0・和0の結果を、正誤の比較なしで返す。分類器を作らない（torchの乱数を消費しない）。
3. When 標本が5件以上あるとき, the Run Client shall 現在の学習帰属のモデルと同じ構造の新しい分類器を1つ作って（torchの乱数を消費）、渡されたパラメータの値にし、標本ごとの有界損失の、件数・和・2乗和を、旧と同じ精度（float32の配列の和）で返す。
4. Where 正誤の比較を求められたとき, the Run Client shall 同じ標本で、渡されたモデルの予測クラスと、保有する対象のモデルの予測クラスを観測ラベルと比べ、「渡されたモデルだけ正解・対象だけ正解・両方正解・両方不正解」の数を、全体と、標本に現れたクラス（昇順）ごとに返す。
5. The Run Client shall 評価で、保有モデル（値・勾配・optimizer・訓練の別）、標本、統計、計数、そのほかの全ownerを変えない。
6. The Run Client shall クロス評価で保有とみなすモデルIDを、評価標本・学習データ・保有モデルのIDと、現在の学習帰属のIDの和集合として返す。

### Requirement 2: サーバのクロス評価

**Objective:** As a 研究者, I want サーバが、モデルの全部の組を、旧と同じ順と規則でclientへ評価させてほしい, so that 集計と乱数の消費が旧と同じになる

#### Acceptance Criteria

1. When クロス評価を求められたとき, the Cross Evaluation shall 最初に、全clientの保有とみなすモデルIDから、モデルIDごとの保有clientの列（渡されたclientの順）を作り、評価する側のモデル（外側）と対象のモデル（内側）の全部の組を、渡されたモデルIDの順に処理する。
2. When 対象のモデルを保有するclientが上限を超えるとき, the Cross Evaluation shall 借りた乱数生成器で、上限の数のclientを無作為に抜き出す。
3. When 組を処理するとき, the Cross Evaluation shall 評価する側と対象が違えば、各clientへ、正誤の比較つきの評価を求め、同じなら、損失の統計だけの評価を求める。評価する側のモデルのパラメータは、グローバルモデルのownerが持つ値を渡す。
4. The Cross Evaluation shall 組ごとに、件数・損失の和・損失の2乗和を、clientの順に足し合わせた表を返す。
5. The Cross Evaluation shall 正誤の比較を、モデルの対（小さいID、大きいID）ごとに、評価した標本数と、それぞれの側だけが正解した数として、全体とクラス別に足し合わせて返す。
6. The Cross Evaluation shall グローバルモデルのパラメータ・統計・次の正式ID・来歴と、clientの状態（乱数を除く）を変えない。

### Requirement 3: 通信量と診断の記録

**Objective:** As a 研究者, I want クロス評価の通信量と診断の記録が旧と同じになってほしい, so that 通信量の指標と、クラスタリングの診断が旧と比べられる

#### Acceptance Criteria

1. When 組を処理するとき, the Cross Evaluation shall 下りと上りの軽量メッセージ数へ、対象のclientの数をそれぞれ足す。
2. When 評価する側のモデルを対象のclientへ送るとき, the Cross Evaluation shall 1回のクロス評価の中で、共有部を、clientごとに最初の1回だけ（そのときの評価する側のモデルの共有部）下りの通信量へ足し、概念固有部を、（評価する側のモデル、client）ごとに最初の1回だけ、下りの通信量と、モデル転送数1として足す。
3. When clientの評価を受け取るたび, the Cross Evaluation shall ラウンド・client・評価する側・対象・評価の結果を、診断の記録へ、評価の順に足す。
4. The 診断の記録 shall 旧の3つの記録（正誤の比較がある評価、全評価、クラス別）を、記録から導ける。

### Requirement 4: 実旧との一致

**Objective:** As a 研究者, I want クロス評価が、複数のclientと複数のラウンドで、旧と同じ結果になってほしい, so that 次のspecのクラスタリングを、旧と同じ入力から始められる

#### Acceptance Criteria

1. When 同じ状態のサーバとclientへクロス評価を求めたとき, the Cross Evaluation shall 実旧のサーバの`_cross_evaluate`と、損失の統計の表、対ごとの正誤の集計、3つの診断の記録、通信量、乱数の状態が一致する。clientの状態は、どちらも変わらない。
2. The 対照 shall 登録→集約の後（配布の前）の状態で、毎ラウンド（新規モデルが登録されたラウンドを含む）クロス評価を行い、2値と多クラス、件数0の評価と件数が正の評価、評価標本を使う場合と学習データを使う場合、標本の抜出し、clientの抜出し、正誤の比較がある評価とない評価、同じclientへの共有部と概念固有部の重複しない計上を通る。
3. When clientの評価だけを行ったとき, the Run Client shall 実旧のclientの`evaluate_model`・`evaluate_model_diagnostics`（クラス別つき）と、結果と乱数の状態が一致する。

### Requirement 5: 拒否

**Objective:** As a 研究者, I want 不正な入力が、状態を変える前に拒否されてほしい, so that 通信量と記録が、途中まで更新されたまま残らない

#### Acceptance Criteria

1. If clientの列、owner、モデルIDの列（非負のbuiltin int、重複なし、グローバルモデルのownerがパラメータを持つID）、ラウンド、clientの上限、乱数生成器が、決まった型と範囲でないとき, the Cross Evaluation shall どの状態も変える前に拒否する。
2. If 渡されたパラメータが、clientの分類器の構造（名前と形）に合わないとき、または対象のモデルID（builtin int。保有していないIDや一時IDは、不正ではなく、件数0の結果になる）・標本の上限・ownerが決まった型と範囲でないとき, the Run Client shall 乱数を消費する前に拒否する。
3. If クロス評価の途中で、あるclientの評価が失敗したとき, the Cross Evaluation shall 後の評価へ進まない。済んだ分の通信量と記録は残る（巻戻しなし）。
4. The Cross Evaluation shall 並行した呼出しでの結果を保証しない。

### Requirement 6: 新実装だけで動くことと依存の向き

**Objective:** As a 研究者, I want クロス評価が、旧実装なしで動いてほしい, so that 後続のspecへ進める

#### Acceptance Criteria

1. When 共用のfresh processの確認を実行したとき, the 共用script shall 旧実装とtestのmoduleを読み込まずに、新規モデルが登録されたラウンドで、集約の後にクロス評価を行い、表の形と、通信量と記録が足されたことを確かめられる。
2. The クロス評価 shall 新しいmoduleの依存を、既存と同じ形で登録した許可の範囲に収める。
