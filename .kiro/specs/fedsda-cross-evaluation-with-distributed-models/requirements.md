# Requirements Document

## Project Description (Input)
- 誰が困っているか: FedSDAの精度と通信量を、FedDrift・FedAvgと比べている研究者（ユーザー）。
- 今の状況: 2026-10-20に既定を「候補検証なし＋候補の共有部の固定」へ変えた（基準版7）。精度は上がったが、下りの通信が最大で約25%増えた。手元の診断（[IMPROVE-020](../../../docs/research/improvement-candidates/improve-020-reduce-cross-evaluation-communication.md)）で、増加の主な出どころはクロス評価で、そのクロス評価の下り（評価するclientへ、集約後の共有部と候補の概念固有部を送る）は、同じラウンドの直後の配布（全clientへ、集約後の共有部と全グローバルモデルの概念固有部を送る）と重複していると分かった。順を入れ替えると、下りが8〜41%減る見積り。
- 何を変えるか: クロス評価で、配布するモデルを使う扱い（配布を先に送り、clientは受け取ったモデルを候補として、まだ置き換えていない手元の保有モデルと比べる。統合の後に、ID対応と、値が変わった代表のモデルの概念固有部だけを送り直す）を足し、既定にする。精度・学習・帰属・統合の結果は変えず、通信量だけを変える。基準版8を足す。

## Introduction
2026-10-20の会話で、ユーザーはこの入れ替えを別specとして実装すると決めた。clientの手元の保有モデルを、統合の後まで置き換えないので、評価に使う値（候補は集約後のグローバルモデル、対象はclientの手元の保有モデル）も、評価するclientの選び方（乱数）も、ラウンドの後の状態も、今と同じになる。違うのは、サーバとclientの間で送るものと、その回数だけ。

## Boundary Context
- 対象: サーバの1ラウンドの同期での、クロス評価と配布の通信の記録、その扱いを選ぶ設定（新しい項目）、最終構成の既定、旧と比べる設定の入口、基準版のgolden（版1〜7の明示と、版8の追加）、既定に依るtest、文書。
- 対象外: クロス評価の評価の中身（評価に使う値、標本、正誤の比較、評価するclientの選び方）、クラスタリングと統合の判定、clientが配布を反映する処理の中身、上りの通信、FedDrift・FedAvg、固定旧と旧golden、研究室サーバ用のgolden。

## Requirements
### Requirement 1: クロス評価で、配布するモデルを使う扱いを選べる
**Objective:** As a 研究者, I want クロス評価のためだけにモデルを送らない扱い, so that 配布と重複する下りの通信を無くせる。
#### Acceptance Criteria
1. The FedSDA system shall FedSDAの参加者の設定に、クロス評価のモデルの送り方を選ぶ項目を持つ（値は「クロス評価のために候補のモデルを送る」——今の扱い——と「配布するモデルを使う」の2つ）。
2. When 「配布するモデルを使う」が選ばれていて、そのラウンドでクロス評価が行われる, the FedSDA system shall 通信量を次のとおり記録する: 集約の後、クロス評価より前に、全clientへ、共有部1個と、その時点の全グローバルモデルの概念固有部を送る。クロス評価では、評価の依頼と返信のメッセージだけを送り、モデルとパラメータを送らない。統合でIDがまとめられたら、全clientへ、ID対応のメッセージと、値が変わった代表のモデルの概念固有部を送る。統合の後に配布する共有部が、先に送った共有部とビット単位で違えば、共有部も送る。損失統計のbyteは、今の配布と同じく数えない。
3. When 「配布するモデルを使う」が選ばれていて、そのラウンドでクロス評価が行われない, the FedSDA system shall 今と同じ通信量を記録する。
4. The FedSDA system shall どちらの値でも、精度・学習・帰属・検出・クロス評価の記録・クラスタリングと統合の記録・最終のパラメータ・乱数の消費を同じにする（変わるのは通信量の指標だけ）。
5. When 「クロス評価のために候補のモデルを送る」が選ばれている, the FedSDA system shall 今と同じ通信量を記録する。

### Requirement 2: 既定を「配布するモデルを使う」にする
**Objective:** As a 研究者, I want 既定が新しい扱いであること, so that 通常の実験のコマンドが、重複の無い通信量で記録される。
#### Acceptance Criteria
1. The FedSDA system shall 最終構成の既定の、クロス評価のモデルの送り方を「配布するモデルを使う」にする。
2. The FedSDA system shall FedSDAの全部の構成が、この既定を引き継ぐ。全部の構成の組立てが例外を出さず、実験のコマンドの引数を変えない。

### Requirement 3: これまでの基準と照合を保つ
**Objective:** As a 開発者, I want これまでの基準が値を変えずに通ること, so that 意図しない差と区別できる。
#### Acceptance Criteria
1. The validation shall 実旧との照合test（部品・全体run・構成）を、変わらず成功させる。旧と比べる設定の入口と、実旧との照合に使う設定の組は、「クロス評価のために候補のモデルを送る」に明示する。
2. The validation shall 基準版1〜7のgoldenを、「クロス評価のために候補のモデルを送る」で、値を変えずに照合し続ける。

### Requirement 4: 新しい既定を基準版8として足す
**Objective:** As a 開発者, I want 新しい既定の値が基準として固定されること, so that 以後の変更で気づける。
#### Acceptance Criteria
1. The validation shall 新しい既定での値を、基準版8のgoldenとして、Windowsの基準環境とWSLの両方で足す（ケースは版7と同じ）。
2. The validation shall 版7と8の差が通信量だけに限られることを、全ケースで確かめる: 記録の表・最終のパラメータ・経路の記録は版7と同じ。指標は、通信量の項目（`communication_volume.`）だけが違ってよい。FedDrift・FedAvgのケースは、全部が同じ。クロス評価が起きたFedSDAのケースでは、下りのbyteが版7より少ない。

### Requirement 5: 文書を合わせる
**Objective:** As a 研究者, I want 文書が新しい通信の扱いを説明すること, so that 通信量の結果を取り違えない。
#### Acceptance Criteria
1. The documentation shall 実験の入口の文書、指標の文書（通信量の定義）、基準の文書（版8）、最終提案構成の文書（サーバの1ラウンドの順）、改善候補IMPROVE-020、再開案内で、新しい扱いと、2026-10-20までの結果の通信量が旧の扱いで記録されていることを書く。
