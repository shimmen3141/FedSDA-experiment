# 要求仕様: 単一runの実行順序とSINEデータ供給

## 導入

研究者が新しい構成で実験を再現・拡張できるよう、旧実装に集中しているデータ供給と実行順序を分離する。
設定基盤の初回部分は実装済みだが、新しいコードからデータを供給し処理を進める経路はまだない。
この段階ではSINE-2を対象に、同じ条件から同じデータと処理順を得られる実行窓口を作る。
最終手法の各判断・学習処理は、その後の移植単位で接続する。

## 範囲と隣接する期待

- 対象: 単一runの条件確認、SINE-2の標本・ランダム概念系列の供給、開始・逐次処理・同期・終端の順序、処理範囲の記録。
- 対象外: 予測重み更新、ドリフト検出、モデルへのデータ帰属、候補採否、学習・事前学習の計算、モデル統合の計算、研究指標の算出、ファイル保存、描画、CLI、掃引。
- 既存設定の値域検証はconfiguration-foundationの契約を使う。不足する固定条件は担当機能の設定として追加し、実行側へ既定値を散在させない。
- 初回の受け入れはデータ・処理順の同値性。学習・判断部を接続するまでは、33指標や最終goldenの一致を新実装の完成条件として主張しない。
- 比較の基準は旧commit `748c3aa`の処理と、最終goldenのSINE-2ケース。縮小規模・学習条件は検証用であり、最終提案の既定値へ昇格させない。

## 要求

### Requirement 1: 実行条件の明示と事前確認

**目的:** 研究者が条件不足や誤指定のまま処理を開始しない。

1. When 単一runの開始が要求される, the Single Run System shall データ供給と実行順序に必要な条件を確認してから処理を開始する。
2. If 必須条件が欠けるか値・組合せが不正である, the Single Run System shall 対象項目・指定値・理由を示し、データ生成や処理部の呼出しを開始しない。
3. If 初回の対象外であるデータセット・概念系列方式・実行方式が指定される, the Single Run System shall 指定内容を示して拒否する。
4. The Single Run System shall 初回の部分設定を、最終FedSDAの全条件が揃った設定として受理しない。

### Requirement 2: SINE-2の標本と概念系列

**目的:** 研究者が基準と同じ観測列を使って移植を検証できる。

1. When SINE-2の標本生成が要求される, the Single Run System shall 基準の2特徴・2クラス・2概念の生成規則に従う標本を返す。
2. When ランダム概念系列の生成が要求される, the Single Run System shall 各クライアントを概念0から開始し、最小安定期間と変更確率に従う指定件数の概念系列を返す。
3. When 標本と概念系列を供給する, the Single Run System shall クライアント・標本位置との対応と、各クライアントの指定件数を維持する。
4. The Single Run System shall 真の概念・ドリフト位置を評価用の情報として区別し、通常の学習・予測に利用できる観測値と混同しない。

### Requirement 3: 再現性とrun間の独立性

**目的:** 研究者が移植や繰り返し呼出しで乱数列を取り違えない。

1. When 基準環境で同じ条件・初期状態・処理部からrunを実行する, the Single Run System shall 同じ概念系列・特徴・ラベル・処理順を再現する。
2. When 初期状態を準備してstreamを作る, the Single Run System shall 基準の「初期準備、全クライアントの概念系列生成、クライアント順の標本生成」の順序を維持する。
3. When runが終了または失敗する, the Single Run System shall 呼出元の設定と乱数状態を保持し、次の独立したrunへ実行状態を持ち越さない。

### Requirement 4: 逐次処理と同期境界

**目的:** 研究者がモデルの更新・同期時点を変えずに処理部を差し替えられる。

1. When 逐次処理を進める, the Single Run System shall 同じ標本位置についてクライアントIDの昇順に処理した後、次の標本位置へ進む。
2. When 一つの同期区間の処理が終わる, the Single Run System shall 全クライアントの保留更新確定、同期、新規モデルの次回アップロード準備を、この順で実行する。
3. When 同期を開始する, the Single Run System shall 同期前の状態記録と、新規モデルの有無による統合開始の判断に必要な情報を、その時点の状態から得る。
4. The Single Run System shall 標本処理・同期の順序を制御し、予測・学習・検出・採否・統合の計算内容を変更しない。

### Requirement 5: 処理範囲と終端

**目的:** 研究者が処理件数と終端動作を明確に確認できる。

1. When 標本数が同期区間長の倍数でない, the Single Run System shall 基準と同じ完全区間だけを処理し、未処理の末尾件数を明示する。
2. When 同期区間長が標本数を超える, the Single Run System shall 逐次処理と通常同期を0回とし、未処理件数と終端処理の結果を記録する。
3. When runの逐次処理が終わる, the Single Run System shall 未完了の候補検証の確定を依頼してから、開始済み通信処理の終端確定を依頼する。
4. The Single Run System shall 終端のためだけに追加標本・通常同期・学習を実行しない。

### Requirement 6: 観測可能な記録と失敗の扱い

**目的:** 研究者が初回の成果と未移植部分を区別して検証できる。

1. When runが成功する, the Single Run System shall 生成件数・処理件数・未処理件数・同期回数・実際の実行順を、クライアントと標本位置に対応付けて返す。
2. If 接続した処理部で失敗する, the Single Run System shall 失敗した段階・クライアントまたは同期区間を示し、成功したrunとして結果を返さない。
3. The Single Run System shall データ供給と順序だけの観測結果を、最終FedSDAの研究指標やgolden一致として報告しない。

## 基準例と受け入れ証拠

- SINE基準: seed=0、3クライアント、各1500標本、同期区間50。30区間・計4500件の逐次処理を確認する。
- データ検証: 初期準備後の乱数状態を合わせ、概念系列・特徴・ラベルを旧基準と照合する。
- 順序検証: 標本位置→クライアント順、区間末の処理、終端の呼出列を照合する。真の概念は評価情報として追跡する。
- 境界例: 不足・不正条件、末尾余り、区間長がstream長を超える条件、処理部の失敗、異なるrunの間に再実行した同一条件を確認する。
- 既存goldenは保全のため実行する。新経路の最終golden比較は手法の移植・不足条件の充足後に別途実施する。
