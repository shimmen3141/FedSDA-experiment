# 実装計画: 単一runの実行順序とSINE供給

## 実行条件

要求・設計と命名revision 2は承認済み。本タスク案の承認状態はspec.jsonを確認する。
実装内部の補助名・テスト名は、各単位の開始前にnaming.mdへ追記し、Lunaレビューと有用な指摘反映によって承認する。
各単位には対象テストを含め、検証済みの責務単位でコミットする。旧実装・golden・研究成果物は変更しない。
各実行単位は1〜3時間を目安とする。共通のテストと依存検査へ変更が集まるため、並列実行を前提とする印は付けない。
具体的なファイル・型・操作名・許可依存の正本はdesign.mdとnaming.md。以下は能力と検証条件を示す。

- [x] 1. 検証環境と新しい層の依存検査を準備する
  - 既存のPython・NumPy・CPU torchの固定環境と、src配置を読み込むpytest構成を確認する。新依存を追加しない。
  - 未作成のpackage境界を用意し、再exportや旧実装のimport窓口を設けない。
  - 現在の全package対象の標準ライブラリ限定検査を、core・configuration・機能別設定の対象へ限定する。これらの制約は維持する。
  - データ層、実行層、モデル側のCPU乱数境界、runtimeの許可依存を別途検査する。旧import・逆依存・専用境界外のtorch参照を拒否する。
  - 完了時には既存設定テストが成功し、禁止importを一時的に注入した検証で境界違反が検出される。未作成モジュールの検査範囲も定め、後続で追加するたび適用する。
  - _Boundary: 検証基盤、層境界の統合セットアップ_
  - _Requirements: 1.1, 2.4, 4.4_

- [ ] 2. SINEデータの固定条件と観測情報を定義する
- [ ] 2.1 ランダム概念系列の固定条件を検証する
  - 全項目必須・不変・keyword-onlyの設定を作り、方式名、0以上の位置差、有限の変更確率[0,1]を検証する。
  - 既存のmetadata値検証を使い、bool・数値文字列・非有限値を受理しない。グローバル設定を読まない。
  - 完了時には正常値・不正値・必須項目不足・不変性のテストが成功する。
  - _Boundary: データ供給の固定条件_
  - _Depends: 1_
  - _Requirements: 1.1, 1.2, 1.3, 2.2_

- [ ] 2.2 観測標本と評価用概念列を区別する
  - 特徴とクラスラベル、client別標本列、評価用の真の概念列を不変の記録として定義する。
  - client ID・標本位置・件数の対応を表し、観測標本に真の概念IDを含めない。
  - 完了時には記録の不変性、可変参照を保持しないこと、観測値と真値の分離を確認できる。torchへ依存しない。
  - _Boundary: データ供給の不変記録_
  - _Depends: 1_
  - _Requirements: 2.1, 2.3, 2.4_

- [ ] 3. 基準と同じ概念列・SINE標本を生成する
- [ ] 3.1 概念列の変更試行と乱数消費順を維持する
  - 明示的に渡されたPython乱数源を使い、各clientを概念0から開始する。client ID順に全概念列を生成する。
  - 直近変化位置との厳密な位置差判定を維持する。最小位置差100では最初の試行位置を101とする。
  - 確率0・1と同一乱数状態からの旧基準照合を含める。旧生成器との接続はテスト側だけに置く。
  - 完了時には概念列と生成後の乱数状態が基準と一致し、指定件数・client順が維持される。
  - _Boundary: 概念系列生成_
  - _Depends: 2.1, 2.2_
  - _Requirements: 2.2, 2.3, 3.1, 3.2_

- [ ] 3.2 SINEのラベル判定と特徴値の精度を維持する
  - 借用したNumPy RandomStateからfloat64の2特徴を生成し、ラベル判定後に特徴をfloat32へ丸める。
  - 概念0の判定と概念1の反転を維持し、対象外の概念IDを拒否する。
  - 全概念列の生成後にclient順・標本位置順で標本を供給する。
  - 完了時には特徴・ラベル・生成後の乱数状態が旧基準と一致し、client IDと各clientの標本件数が一致する。
  - _Boundary: SINE標本供給_
  - _Depends: 2.2, 3.1_
  - _Requirements: 2.1, 2.3, 2.4, 3.1, 3.2_

- [ ] 4. 実行条件・乱数境界・処理部契約を用意する
- [ ] 4.1 run専用の乱数とCPU torch状態復元を接続する
  - Python・NumPyの独立した乱数源をrunごとに作る。
  - モデル側の専用境界でCPU torch状態を保存・seed設定・復元する。成功と例外の両出口を対象とする。
  - 実行層の乱数源とモデル側の境界を統合し、CUDA状態・thread数・dtypeを変更しない。
  - 完了時には呼出元のグローバル乱数・設定が保持され、借用したrun専用乱数だけが消費される。CPU状態は成功・失敗の双方で復元される。
  - _Boundary: 実行乱数とモデル乱数境界の統合_
  - _Depends: 1_
  - _Requirements: 3.1, 3.3_

- [ ] 4.2 単一runの狭い実行条件を事前検証する
  - 既存の規模・seed条件と概念系列設定を必須の不変条件として束ね、sine2と承認済み実行方式だけを受理する。
  - seedは0〜2**32-1を要求し、剰余・丸めを行わない。端数と区間長がstream長を超える条件は許容する。
  - 直接構築と実行前に同じ検証を使い、複合型の検証を既存coreの単純値検証へ押し込まない。
  - 完了時には部分設定型・不正な型・方式・seedを拒否し、許容する境界条件を受理する。検証だけでデータ生成を開始しない。
  - _Boundary: 実行条件_
  - _Depends: 2.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 5.1, 5.2_

- [ ] 4.3 接続先の責務と成功・失敗の記録契約を定義する
  - 初期準備・client操作・server操作と参加者集合の接続契約を定義する。具体的な学習やダミーserverはproductionへ追加しない。
  - 成功記録には件数・実行イベント・観測列・評価用概念列を保持し、可変な参加者・乱数源・研究指標を含めない。
  - 実行失敗は正式ステージ・任意の位置・理由と元例外のcauseで表す。
  - 完了時にはテスト側の観測用処理部が契約を満たし、不変記録と例外の位置情報を検証できる。runtimeへの逆依存とclientへの真値入力はない。
  - _Boundary: executionの接続・記録契約_
  - _Depends: 2.2, 4.1_
  - _Requirements: 2.4, 4.3, 4.4, 5.3, 6.1, 6.2, 6.3_

- [ ] 5. 完全区間の進行と単一runの組立を実装する
- [ ] 5.1 標本位置・同期区間・終端の呼出順を制御する
  - 標本位置ごとにclient ID昇順で処理し、全clientの保留更新、同期前記録、登録可能モデルの照会、同期、送信待ち期間の進行を順に呼ぶ。
  - 同期へ渡す値は照会時点の事実とし、統合や学習の判断内容は接続先へ委譲する。
  - 完全区間だけを処理し、全clientの未完了候補検証を確定してから開始済み通信を確定する。終端用の追加標本・学習・通常同期を行わない。
  - 完了時には3×1500・区間50で4500標本処理と30同期の呼出列が一致する。端数・区間長超過でも指定の終端順が成立する。
  - client・serverの失敗では位置とcauseを報告し、それ以降の処理・終端・再試行を呼ばないことを検証する。
  - _Boundary: 区間進行_
  - _Depends: 3.2, 4.3_
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 5.1, 5.2, 5.3, 5.4, 6.1, 6.2_

- [ ] 5.2 検証・初期準備・供給・進行を単一runへ統合する
  - 設定とfactoryの条件を乱数生成・標本生成・初期準備より先に確認する。
  - 同じrun専用乱数と標本生成器で初期準備を一度行い、参加者件数・ID・必要操作を検査してから、全概念列、全標本列、区間進行を順に接続する。
  - 初期準備と進行をCPU乱数境界で囲み、成功記録の構築を含む全出口で状態を復元する。準備・データ・参加者契約の失敗は対応するステージで報告する。
  - 完了時には不正入力が生成や準備を呼ばないこと、成功時の件数・順序、失敗時に成功結果を返さないことを観測用処理部で確認できる。
  - CLI・preset・保存・学習を追加せず、狭い単一runの窓口だけを接続する。
  - _Boundary: runtime統合_
  - _Depends: 3.1, 3.2, 4.1, 4.2, 4.3, 5.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 2.3, 2.4, 3.1, 3.2, 3.3, 6.1, 6.2, 6.3_

- [ ] 6. 基準照合と回帰保全を確認する
- [ ] 6.1 初期準備後の照合とrun間独立性を統合検証する
  - 観測用factoryで100標本と10回のPython shuffleを消費し、その後の概念列・観測列を旧基準と照合する。初期学習を実装したという扱いにはしない。
  - 異なる条件のrunを挟んだ再実行で同一条件を再現し、参加者はrunごとに新規に準備する。
  - 初期準備・データ生成・参加者契約・client・server・終端の失敗を注入し、位置・cause・乱数復元と、失敗後の再試行・終端がないことを検証する。
  - 完了時にはデータと処理順の一致、独立性、不変結果のテストが成功する。新経路の最終FedSDA研究指標やgolden一致は主張しない。
  - _Boundary: データ・実行・乱数の統合検証_
  - _Depends: 5.2_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 3.1, 3.2, 3.3, 4.1, 4.2, 4.3, 4.4, 5.1, 5.2, 5.3, 5.4, 6.1, 6.2, 6.3_

- [ ] 6.2 設定基盤・既存手法・最終構成の回帰を保全する
  - 固定Windows CPU環境とrefactoring-baselineの手順で、既存schema・設定基盤・対象機能・新対象テスト・旧golden・最終構成goldenを実行する。
  - 層境界検査が全新規モジュールを対象にすることと、旧基準への接続がテスト側だけにあることを確認する。
  - 完了時には対象テストが全て成功し、goldenのhashと研究成果物が保持される。旧goldenの成功を新学習経路の同値性として報告しない。
  - _Boundary: 全体統合回帰_
  - _Depends: 6.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 3.1, 3.3, 4.4, 6.3_
