# Requirements Document

## Project Description (Input)

誰の問題か: FedSDAとFedDriftの比較実験コードをリファクタリングしている研究者（主担当と、後で読む人）。

現在の状況: サーバは、新規モデルを登録し、clientのモデルを集約できる（server-model-registration-and-aggregation）が、集約したグローバルモデルをclientへ返す処理がない。clientのモデルは、ラウンドをまたいで、clientごとに別々に進んだままである。

変えたいこと: 旧の最終構成のサーバの配布（`broadcast_models`）と、clientの配布の受取り（`apply_server_mapping`）を、旧と同じ順序・数値・乱数の消費で行う。配布は、モデルIDの対応（統合によるIDの付け替え。なければ空）を同時に適用する。

調査で確かめたこと（固定旧748c3aa）:

- サーバの配布（`servers/shared_backbone.py` 132〜152行）: 下りの通信量へ、共有部（最初のグローバルモデルのもの）1個と、全グローバルモデルの概念固有部を、clientの数だけ足す。論理的なモデル転送数は、グローバルモデルの数×clientの数。ID対応があれば、clientの数だけ軽量メッセージを足す。その後、全clientへ、ID対応・全グローバルモデル・全統計を渡す。
- clientの受取り（`clients/base.py` 662〜727行）の順: (1)現行モデルのIDがID対応で変わるなら、その位置と、サーバによる統合の適応イベントを記録する。(2)損失統計をID対応で付け替え（同じIDへ集まったら、件数が最大のもの）、持っていないか0件のIDは、サーバの統計で補う。(3)評価標本をID対応で付け替えて連結し、上限を超えたら無作為に抜き出す。(4)学習データと計数をID対応で付け替える。(5)非負のIDの保有モデルを捨て、グローバルモデルごとに、新しいモデルを作って値を上書きする（一時IDのモデルは残す）。(6)全保有モデルを、非負のIDが最小のモデルの共有部へつなぎ直す。(7)現行モデルのIDへID対応を適用する。
- (5)は、モデルを新しく作るので、グローバルモデルの数だけ、torchの乱数（初期化）を消費する。作り直したモデルのoptimizerは、蓄積のない新しい状態になる。(6)は、つなぎ先以外の全モデルの概念固有部のoptimizerを作り直す。
- 学習率: 旧は、新しく作ったモデル（初期モデル、配布で作り直したモデル）の2つのoptimizerに`BASE_LR`を、候補と、(6)で作り直す概念固有部のoptimizerに`NEW_MODEL_LR`を使う。最終構成では同じ値だが、設定としては別である。
- 配布の後、どのclientも、全グローバルモデルを保有する（それまで持っていなかったモデルも）。
- (7)は、切替の通知を呼ばずに現行モデルのIDを置き換える（globalの診断証拠は再始動しない）。保留標本、損失の監視、候補検証、送信保留、予測の重みと診断証拠は、受取りでは変わらない。
- 集約後の予測重みの再較正（`recalibrate_routing_after_aggregation`）は、サーバの`run_round`が配布の後に呼ぶ、別の処理である。

## Introduction

研究者が、グローバルモデルの配布と、clientでの受取りを、旧と同じ結果になる呼出しで行えるようにする。これで、クラスタリングなしのラウンド（登録→集約→配布）が通る。

## Boundary Context

- **In scope**: サーバの配布（下りの通信量の記録と、全clientへの受渡し）。clientの受取り（ID対応の適用、統計の補完、評価標本・学習データ・計数の付け替え、保有モデルの作り直しと共有部へのつなぎ直し、現在の学習帰属の付け替え、サーバによる統合の適応記録）。そのために要る、既存のownerの操作の追加（保有モデルの全置換え、損失統計の全置換え、グローバルの統計の一覧、共有部のoptimizerの状態の保持、適応記録の結果種別）と、clientの設定の束への学習率の設定の追加。
- **Out of scope**: 集約後の予測重みと診断証拠の再較正（次のspec）。クロス評価・クラスタリング・統合（ID対応を作る側。後続のspec。本specは、与えられたID対応を適用するだけ）。実行の枠のサーバの操作の実体と、全体runの接続。Cached方式のための、配布時点のパラメータの控え。計算量の記録。
- **Adjacent expectations**: 統計の選択、評価標本・学習データ・計数・現在の学習帰属のID対応、共有部へのつなぎ直しは、移植済みの部品をそのまま使い、中の処理を変えない。ID対応は、付け替え前のIDから付け替え後のIDへの対応で、後続のspecが作る。

## Requirements

### Requirement 1: サーバの配布

**Objective:** As a 研究者, I want グローバルモデルが、旧と同じ通信量の計上で、全clientへ渡ってほしい, so that 通信量の指標と、clientの状態が旧と同じになる

#### Acceptance Criteria

1. When 配布を求められたとき, the Global Model Distribution shall 下りの通信量へ、最初のグローバルモデルの共有部のパラメータと、全グローバルモデルの概念固有部のパラメータを、それぞれclientの数だけ足し、論理的なモデル転送数へ、グローバルモデルの数×clientの数を足す。
2. When ID対応が空でないとき, the Global Model Distribution shall 下りの軽量メッセージ数へ、clientの数を足す。
3. When 通信量を記録した後, the Global Model Distribution shall 全clientへ、渡された順に、ID対応と、全グローバルモデルのパラメータと損失統計を受け取らせる。
4. The Global Model Distribution shall グローバルモデルのパラメータ・統計・次の正式ID・来歴を変えない。

### Requirement 2: clientの受取り（統計と標本と計数）

**Objective:** As a 研究者, I want clientの統計・標本・計数が、ID対応と配布に合わせて、旧と同じ規則で付け替わってほしい, so that 統合の後も、モデルごとの履歴が旧と同じになる

#### Acceptance Criteria

1. When 配布を受け取ったとき, the Run Client shall 損失統計を、ID対応で付け替える。同じIDへ複数の統計が集まったら、全体の件数が最大のもの（同数なら先のもの）を残す。持っていないIDと、全体の件数が0のIDは、サーバの統計で置く。
2. When 配布を受け取ったとき, the Run Client shall 評価標本を、ID対応で付け替えて、元の順に連結し、上限を超えたモデルは、借りた乱数生成器で上限の件数を無作為に抜き出す。
3. When 配布を受け取ったとき, the Run Client shall 学習データを、ID対応で付け替えて元の順に連結し、学習量と割当概念の計数を、ID対応で付け替えて足し合わせる。
4. When 現在の学習帰属のIDが、ID対応で別のIDへ変わるとき, the Run Client shall サーバによる統合の適応記録（位置は処理した標本数、変更前後のID）を足し、その位置を、サーバによる付け替えの位置として記録する。警報による切替の位置には足さない。

### Requirement 3: clientの受取り（保有モデル）

**Objective:** As a 研究者, I want clientの保有モデルが、旧と同じく作り直され、つなぎ直されてほしい, so that 配布の後の学習と予測が、旧と同じ状態から始まる

#### Acceptance Criteria

1. When 配布を受け取ったとき, the Run Client shall 非負のIDの保有モデルを全部外し、配布されたグローバルモデルごとに、配布の順で、新しい分類器を作って、配布されたパラメータの値にし、蓄積のない新しいoptimizerの状態を持たせる。一時IDの保有モデルは、そのまま残し、配布されたモデルの後ろへ並べる。
2. When 分類器を新しく作るとき, the Run Client shall 配布されたモデルの数だけ、旧と同じ順で、torchの乱数を消費する。
3. When 保有モデルを作り直した後, the Run Client shall 全保有モデルを、非負のIDが最小のモデルの共有部へつなぎ直し、つなぎ先以外のモデルの概念固有部のoptimizerを、蓄積のない新しい状態にする。以後の学習は、つなぎ先の共有部と、そのoptimizerを使う。
4. When optimizerの状態を作るとき, the Run Client shall 作り直したモデルの共有部と概念固有部には、初期モデルと同じ学習率の設定を使い、つなぎ直しで作り直す概念固有部には、候補と同じ学習率の設定を使う。
5. When 保有モデルをつなぎ直した後, the Run Client shall 現在の学習帰属のIDを、ID対応で付け替える。診断証拠へは通知しない。
6. The Run Client shall 受取りで、保留標本、損失の監視、警報の記録、候補検証の保持、送信保留、学習要求、一時IDの採番、予測の重みと記録、診断証拠を変えない。

### Requirement 4: 実旧との一致

**Objective:** As a 研究者, I want 登録→集約→配布のラウンドが、複数のclientと複数のラウンドで、旧と同じ結果になってほしい, so that クラスタリングなしの全体の流れを、旧と同じ状態で進められる

#### Acceptance Criteria

1. When 同じ初期モデル・統計・設定・標本列・乱数を与えたとき, the 配布 shall 実旧のサーバと、実`__init__`で作った実旧のclient複数に対して、ラウンドごとに、標本処理→保留中の学習→登録→集約→配布→送信待ちの進行、を行い、配布の後に、サーバの全状態（グローバルモデル、統計、次の正式ID、来歴、通信量）、各clientの全状態、乱数の状態が一致する。
2. When ID対応を与えて配布を受け取らせたとき, the Run Client shall 実旧のclientの受取りと、全状態と乱数の状態が一致する（現在の学習帰属が付け替わる場合、複数のモデルが1つへ集まる場合、評価標本が上限を超える場合を含む）。
3. The 対照 shall 一時IDのモデルを持つclientへの配布、採番だけが行われて一時IDのまま残ったモデル（LEGACY-016）を持つclientへの配布、それまで持っていなかったモデルの受取り、候補検証を保持しているclientへの配布、参加するclientがいる集約に学習データを持たないモデルが混ざる状態、学習率の2つの設定が違う値の場合を通る。

### Requirement 5: 拒否と途中の失敗

**Objective:** As a 研究者, I want 不正な入力が、状態を変える前に拒否されてほしい, so that サーバとclientが、途中まで更新されたまま残らない

#### Acceptance Criteria

1. If clientの列、owner、ID対応（整数から整数への対応）、配布されるパラメータと統計が、決まった型と範囲でないとき, the 配布 shall どの状態も変える前に拒否する。
2. If 配布されるパラメータが、clientの分類器の構造（名前と形）に合わないとき、または受取りの後で、現在の学習帰属のモデルを保有しないことになるとき, the Run Client shall どの状態も変える前に拒否する。
3. The Run Client shall 受取りの計算（統計の選択、新しい分類器とoptimizerの状態の生成）を、最初の状態更新より前に済ませる。新しい分類器の生成による乱数の消費は、検査の後に行う。
4. If 配布の途中で、あるclientの受取りが失敗したとき, the Global Model Distribution shall 後のclientへ進まない。済んだclientの受取りと、通信量は残る（巻戻しなし）。
5. The 配布 shall 並行した呼出しでの結果を保証しない。

### Requirement 6: 新実装だけで動くことと依存の向き

**Objective:** As a 研究者, I want 登録→集約→配布のラウンドが、旧実装なしで動いてほしい, so that 後続のspecへ進める

#### Acceptance Criteria

1. When 共用のfresh processの確認を実行したとき, the 共用script shall 旧実装とtestのmoduleを読み込まずに、複数のclientで、ラウンドごとに登録・集約・配布を行い、配布の後に全clientが同じグローバルモデルを保有することを確かめられる。
2. The 配布 shall 新しいmoduleの依存を、既存と同じ形で登録した許可の範囲に収める。
