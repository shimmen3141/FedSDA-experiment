# Requirements Document

## Introduction
LEGACY-016の修正（[pending-model-registration-by-own-id](../pending-model-registration-by-own-id/requirements.md)。送信保留の全部を、それ自身のIDで登録する）は、本規模の比較（2026-10-13、研究室サーバ、480 run）で、精度を有意に上げた条件が2つだけだった一方、全条件でグローバルモデル数と下りの通信量を増やした（sine2で+30〜37%）。ユーザーは、有意でないわずかな精度のために通信量を増やすのは合理的でない、と判断した。

問題の言語化と判断の基準は、[LEGACY-016の記録](../../../docs/research/implementation-findings/legacy-016-registration-id-consumed-without-model.md)の「本規模の比較と、扱いの見直し」にある。要点: 送信までの待ちは、新しいモデルを1ラウンド学習させてから共有するためにある。待ちの途中で現行から外れたモデルには、新しい標本が割り当てられない（保存した学習標本での学習は続く）。そのモデルは、待ちの期間の新しい標本での学習を終えておらず、安定した概念を表す証拠も無い。共有の費用は、毎ラウンド続く。判断の基準は、「新しいモデルを共有するのは、それが、clientの現行モデルとして、待ちの期間の学習を終えたときに限る」。読取りだけの計数（標本5000、16 run）では、登録されなかった32件のうち、約2割（6件）が、後に現行へ戻って長く使われ、約8割は戻らないか、短く戻っただけだった。

この判断に沿う3つ目の扱い（現行である間だけ待ちを進め、待ちを終えて、登録の時点で現行であるモデルだけを登録する）を足して、FedSDAの既定にする（2026-10-13・14、ユーザー了承。待ちの進め方は、「ラウンド境界で現行であるときだけ、待ちを1ラウンド進める（外れている間は止める）」をユーザーが選んだ）。これまでの2つの扱いは、設定で選べる形で残す。

## Boundary Context
- 対象: 新FedSDAのclientの送信保留のowner、正式IDの確認、clientの登録の件数と待ちの進行、登録の扱いの設定と最終構成の既定、基準版のgolden（版2・3の設定の明示と、版4の追加）、影響の計測と、サーバでの比較のscript。
- 対象外: 固定旧748c3aaと旧golden、FedDrift・FedAvgの動作、短い警報の扱い（LEGACY-002・IMPROVE-006。この後のサーバの比較の結果で決める）、候補の採否・検出・学習の方式、待ちのラウンド数の値（最終構成は1のまま）、旧実装の削除。
- 用語: 「送信保留」は、clientが採用して一時ID（負）で保有し、サーバの登録を待っているモデル。「待ち」は、送信保留のモデルが登録できるようになるまでに残る、ラウンド境界の回数。「ラウンド境界」は、同期（登録→集約→…→配布→再較正）の後に、待ちを進める時点。「現行」は、clientの学習帰属のモデル（`CurrentTrainingModelAssignment`の値）。

## Requirements
### Requirement 1: 現行モデルとして待ちを終えたモデルだけを登録する
**Objective:** As a 研究者, I want 待ちの期間を、現行モデルとして過ごしたモデルだけが共有されること, so that 共有に値する証拠の無いモデルで、通信量を増やさない。

現行かどうかは、待ちの進行の時点（ラウンド境界）と登録の同期の時点の2つで判定する（ラウンドを単位にした近似。区間の途中で現行を外れ、次の時点までに戻ったモデルは、外れなかったものと同じに扱う。ユーザーが選んだ、ラウンド境界を単位にする進め方による）。
#### Acceptance Criteria
1. When ラウンド境界で待ちを進める, the FedSDA system shall 現行モデルの送信保留だけ、待ちを1減らし（0未満にしない）、ほかの送信保留の待ちを変えない。
2. When 同期で登録する, the FedSDA system shall 待ちが0で、かつ、その時点の現行モデルである送信保留だけを登録する（1つのclientから、1回の同期で、高々1件）。
3. While 送信保留のモデルの待ちが0で、現行でない, the FedSDA system shall その送信保留を、登録せず、正式IDを採番せず、捨てずに保持し、後の同期で、そのモデルが現行であれば、そのときに登録する。
4. When 送信保留がある間に、同じclientが別のモデルを採用する, the FedSDA system shall 両方を、採用の順に、送信保留として保持する（前の送信保留を置き換えない）。新しい送信保留の待ちは、設定のラウンド数から始める。
5. When 送信保留のモデルを登録する, the FedSDA system shall そのモデルの一時IDを、保有モデルの学習状態・損失統計・学習標本・評価標本・学習量と割当概念の計数の全部で正式IDへ付け替え、現行を正式IDへ変える（登録するモデルは、常に現行である）。
6. If 登録の確認のとき、待ちが0の現行の送信保留が無い、そのモデルが保有されていない、または一時ID（負）でない, the FedSDA system shall 確認のどの状態も変える前に拒否する（正式IDが、あるownerで使用済みの場合の拒否は、各ownerの付替えの操作が行う既存の契約のままで、この項目の対象外。サーバの登録が、確認より前に正式IDの採番と来歴の記録を行う既存の契約も、この項目の対象外。新しい扱いでは、件数と確認の対象が同じ条件で決まるので、正常の流れでは、確認の拒否に到達しない）。
7. The FedSDA system shall 送信保留のモデル以外のモデル（現行の、別の一時IDのモデルなど）を、送信保留の登録として付け替えない。
8. When 採用したモデルが、採用から登録までの、全部の待ちの進行の時点と、登録の同期の時点で、現行である, the FedSDA system shall そのモデル（同じ一時IDのモデル）を、送信保留の全部を自身のIDで登録する扱いと、同じ同期で登録する（正式IDは、同じ同期のほかのclientの登録の有無と、同じclientで先に登録しなかった送信保留の有無で、採番の順がずれうる。そのclientの送信保留がそのモデルだけのときの確認では、同じ入力から、同じ正式IDで、全ownerの状態が同じになる）。

### Requirement 2: 扱いを設定で選べ、FedSDAの既定を新しい扱いにする
**Objective:** As a 開発者, I want 3つの登録の扱いを設定で選べること, so that 旧との照合と、これまでの既定との比較を続けられる。
#### Acceptance Criteria
1. The FedSDA system shall 登録の扱いの宣言した値に、新しい扱いの値を足し、これまでの2つの値の動作を変えない。
2. The FedSDA system shall 最終構成と、その派生の構成（FedSDAの11構成）の既定を、新しい扱いにする。実験のコマンドの引数には出さない（掃引の選択肢の登録——`experiment_spec`——と、コマンドの引数を変えない。実装レビューで差分を確かめる）。
3. The FedDrift system and the FedAvg system shall これまでと同じ動作を保つ（FedDriftは、送信保留を1つだけ保持し、現行を付け替える扱いを、明示して使う。sourceを変えない）。
4. If 新しい扱いのownerに、現行のモデルIDを受け取らない、待ちの進行・待ちの済んだ送信保留の有無・数・取得・最も古い送信保留の残りの待ちの操作を呼ぶ, the FedSDA system shall どの状態も変える前に拒否する（現行に依らない答えを、新しい扱いの答えとして使わせない）。

### Requirement 3: 基準と照合を、扱いの前後で分けて保つ
**Objective:** As a 開発者, I want これまでの基準が通り続け、新しい既定の差が説明できること, so that 意図した差と、意図しない差を、区別できる。
#### Acceptance Criteria
1. The validation shall 実旧との照合test（部品・全体run・構成）を、旧と同じ扱いの設定で、変わらず成功させる。
2. The validation shall 基準版1〜3のgoldenを、それぞれの版の扱いの設定で、値を変えずに照合し続ける（版2・3の設定は、送信保留の全部を自身のIDで登録する扱いを、明示して組み立てる）。
3. The validation shall 新しい既定での値を、基準版4のgoldenとして、Windowsの基準環境とWSLの両方で足す（研究室サーバ用は、版2〜4のどれも、このspecの対象外）。ケースごとに、基準版3の扱いの実行で、待ちの途中のラウンド境界（後に同期が続くもの）、または登録の時点で、現行でない送信保留があった回数を数え、0のケースでは、基準版4の値（指標・表・パラメータ）が基準版3と同じであること、1以上のケースでは差があることを確かめる。1以上のケースが、少なくとも1つあること（1以上のケースで差が出ることは、論理の帰結ではなく、実行で確かめる観測）。
4. The validation shall 新しい既定の全体runで、正式IDの確認のたびに、送信保留のモデルが現行であることと、runの終わりに、どのclientにも、登録されなかった採用（送信保留でない、一時IDの保有モデル）が無いことを確かめる。runの終わりに送信保留のまま残るモデルは、別に数える。同じ条件の、送信保留の全部を自身のIDで登録する扱いの実行では、現行でないモデルの登録、または、待ちの途中で現行でない送信保留があること（条件が、扱いの分かれる経路を通ること）も確かめる。

### Requirement 4: 影響を測り、サーバでの比較に備える
**Objective:** As a 研究者, I want 新しい扱いで、精度・通信量・モデル数がどう変わるかを知ること, so that 既定の判断を確かめ、短い警報の扱いを同じ基準で決められる。
#### Acceptance Criteria
1. The validation shall LEGACY-016の修正のときと同じ8条件（client 10、標本2500、集約間隔50、sine2・sea4・circle2・mnist2のseed 0・1）で、3つの扱いを手元（Windowsの基準環境）で実行し、精度・定常精度・下りと上りの通信量・最終のグローバルモデル数・登録の件数・登録されなかった採用の数・runの終わりに送信保留のまま残った数・runの終わりの保有モデルの数を比べて、記録する（手元の簡単な計測は構わない、と2026-10-14にユーザーが示した）。本規模の影響は、このspecの後に、研究室サーバでの比較（要求4.2のscript）で測る。このspecでは、そのコマンドをユーザーへ示すまでを行い、結果の読み解きは対象外とする。
2. The comparison script shall 修正の有無の比較（`run_behavior_fix_comparison.py`と`analyze_behavior_fix_comparison.py`）で、登録の扱いの水準に、新しい扱いを選べるようにし、短い警報の扱い・警報を待つ扱いと組み合わせて実行・集計できるようにする（既存の水準の名前と、既存の組合せの名前は、変えない）。集計は、データと集約間隔ごとに、組合せの絶対値（平均と標準偏差）と、対の差（平均と標準誤差）を出し、種類の違うデータを越えて平均した行は出さない（2026-10-13ユーザー指摘: データを越えて平均すると、各データの傾向が見づらい）。
3. If 新しい扱いで、ほかの扱いより精度などが下がる条件がある, the report shall その条件と差を、ユーザーへ伝える。
