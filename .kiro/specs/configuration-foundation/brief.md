# Brief: 設定・選択肢管理の基盤

## 問題

研究者が新方式・オプションを追加・削除するとき、mode名・設定・制約・実体生成・
CLI・掃引・文書の複数箇所を追う必要がある。意味が曖昧な名前も残っている。

## 現状

既存schemaの制約管理は活用できるが、長いmode名、グローバルconfig、多重継承との結合がある。
旧基準は`748c3aa`。新実装は新しい名前と形式に統一する方針が承認済み。

## 到達状態

選択肢の意味・適用条件・専用パラメータが説明でき、実効設定を検証・保存できる。
登録から選択肢を追加・削除でき、不正・未使用の指定を明確に拒否する。

## 方針

担当機能の設定型・選択肢定義と、preset・実効設定の解決を分離する。
具体アルゴリズムの生成は後続runtimeが担当する。

## 範囲

- In: 設定の意味、選択肢、preset展開、値・組合せ検証、実効設定、保存表現。
- Out: 新しい検出器・routingの計算、学習、stream実行、CLI、成果物ファイルI/O。
- Boundary Candidates: 入力の解釈、選択肢の定義、実効設定の検証・確定、保存表現。
- Upstream: 方針・最終提案の正本、既存schemaを読む調査。
- Downstream: runtime、CLI、掃引、参照文書、成果物条件の保存。
- Existing Spec Touchpoints: 既存cc-sdd specなし。

## 制約

後方互換なし。過去成果物と旧goldenは保存する。
要求と`naming.md`を人間がレビューし、承認前に新実装を作らない。
後続機能のAPIと名前は、その実装単位の開始前に別途レビューする。
