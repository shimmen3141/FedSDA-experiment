# FedHASPの部品を1クライアントで比べる予備実験（基準版16、計画 2026-11-17）

- 目的: 教授の指摘（「hard assignment と soft prediction が本質なら、連合学習ではなく1クライアントのコンセプトドリフト対応の論文にすべき」）を受け、1クライアントでも、(1) 学習を固い割り当てにする効果、(2) 予測を混ぜる効果が、連合学習の設定（10 client）より大きいか・同じか・小さいかを確かめる。結果で、1クライアント版の論文を主にするか、連合学習版を主にするかを決める材料にする（決めるのはユーザー）。
- 位置づけ: 予備実験。1クライアントの比較手法（ARF、DWMなど）との比較は、末尾の「段階2」として並行して準備した。
- 背景の数値（連合学習、10 client、10データ×間隔50／500×seed 0〜9）: 学習を固くする効果は、混合の予測で+0.63／+0.30pp、現在のモデルだけの予測で+0.78／+0.80pp。予測を混ぜる効果は、固い学習で+1.97／+1.16pp。純度は固い0.900、柔らかい0.867（`docs/experiments/experiment-log.md`の2026-11-05・11-07の行）。

## 1クライアントでの扱い

- 製品の掃引の入口を`--client-count 1`で動かす。コードは変えない。2026-11-17に手元で、下の構成（`fedsda-local-parameter-prediction`を除く6つ。これは後で同じく確かめた）がSINE2・1000標本・間隔50と1000で動くことを確かめた（失敗0）。
- 1クライアントでは、サーバの集約はそのclientのパラメータをそのまま返すだけになる。残るのは、集約のときのサーバの統合（クラスタリング）と、同期のスナップショットの更新。そこで間隔を2つ置く。
  - 間隔50: 統合とスナップショットの更新を、50標本ごとの保守の手順として残す。
  - 間隔5000（＝ストリームの長さ）: ストリームの途中で集約が一度も起きない。統合が無く、同期のスナップショットは作った時点のまま。
- 柔らかい学習（`fedsda-soft-training`）は、各モデルについて責任度に比例して $B$ 件を抜いた平均の損失で更新するので、1回の更新の大きさは固い学習と同じ（`.kiro/specs/fedsda-soft-training-assignment/requirements.md`の要求1.3）。「柔らかい学習は実質の学習率が小さいだけ」という説明は、この構成には当てはまらない。

## 条件

- 10データ（SINE2、CIRCLE2、SEA2、SEA4、MNIST2、MNIST4、fmnist2、fmnist4、rotmnist2、rotmnist4）×間隔50・5000×seed 0〜29、1 client×5000標本。
- 1クライアントのストリームは5000標本で、コンセプトの変化は平均およそ5回（最小の間隔300、その後は1標本ごとに確率0.0015）。1 runのばらつきが大きいので、seedを連合学習の実験の10から30に増やす。
- 構成（製品の掃引、6構成、3,600 run）:
  - `fedsda-training-mass-diagnostics`: FedHASP（固い学習＋混合の予測）。挙動は`fedsda`と同じで、純度の記録を足したもの。
  - `fedsda-soft-training`: 柔らかい学習＋混合の予測。
  - `fedsda-single-model-prediction`: 固い学習＋現在のモデルだけの予測。
  - `fedsda-soft-training-single-model-prediction`: 柔らかい学習＋現在のモデルだけの予測。
  - `fedsda-local-parameter-prediction`: 固い学習＋混合の予測で、各モデルの予測に局所のパラメータだけを使う（同期の時点と局所の2つの版を混ぜない）。間隔5000では統合も版の混合も無く、純粋な1クライアントの手法に最も近い形になる（2026-11-17ユーザー判断で追加）。柔らかい学習とこの予測の組合せの構成は無い。
  - `fedavg`: 単一のモデル（参考）。
- 研究ツール`tools/research_oracle_concept_assignment`の変種`product-default-oracle-concept-assignment`（600 run）: 警報と帰属先を真のコンセプトに合わせたFedHASP。完全に特化させた場合の目安（精度の上限ではない。`docs/research/fedhasp-oracle-assignment-v16.md`の「論文での説明の限定」）。

## まとめ方（事前に決める）

- データ・間隔・seedで対にする。欠けたら止める。
- 20セル（10データ×2間隔）ごとに、次の差の30 seedの平均・95%信頼区間・seedの勝ち負けを出す。全体は20セルの平均を等しい重みで平均する（間隔ごとにも出す）。
  - 学習を固くする効果: 固い−柔らかい（混合の予測、現在のモデルだけの予測の両方）。
  - 予測を混ぜる効果: 混合−現在のモデルだけ（固い学習、柔らかい学習の両方）。
  - Oracle−FedHASP、FedHASP−単一のモデル。
  - 2つの版を混ぜる効果: FedHASP−`fedsda-local-parameter-prediction`。
- 診断: 純度（固いと柔らかい）、最後のモデルの数、警報と新しいモデルの採用の回数。標準指標として、計算量（MAC）と経過時間も併記する（1クライアントで集約が意味を持たないので、通信量は参考）。
- 判断の材料（判定はユーザー）: 1クライアントでの効果の大きさを、上の連合学習の数値と並べて示す。1クライアント版を主にする条件として話し合った3つ（固いと柔らかいの差がはっきり出る、標準の比較手法を上回る、理論）のうち、この実験が答えるのは1つ目だけ。

## 段階2: ストリーム学習の比較手法（2026-11-17ユーザー指示で準備、予備実験と並行）

- 目的: 1クライアント版を主にする条件の2つ目（標準の比較手法を上回るか）の材料。同じ入力の系列で、FedHASPとストリーム学習の標準の手法を比べる。
- 研究ツール`tools/research_single_client_stream_baselines/`（製品のコードは変えない）。
  - `stream_export.py`（プロジェクトのvenv）: 製品の`fedsda`の1クライアントのrunを、初期準備と系列の生成まで動かし、標本の処理の直前で止めて、事前学習の標本（概念0、500件）と評価の系列（特徴・ラベル・真のコンセプト）を書き出す。乱数の順序を手で再現しない。系列は集約の間隔に依らない。
  - `river_baselines.py`（numpyとRiverだけの別のvenv。プロジェクトの固定のvenvへRiverを入れると、numpyなどの版が変わりうるため）: 各手法は事前学習の標本を学習してから（評価しない）、系列の全標本を予測→学習の順で処理する。精度は全標本の正解の割合で、製品の`prediction_accuracy`と同じ定義。
  - `analyze.py`: 予備実験の6構成・Oracle・Riverの結果を対にして集計する（上の「まとめ方」に、FedHASP−各手法を足す。Riverは間隔を持たないので、間隔50と5000のFedHASPの両方と対にする）。欠け・余分のほか、書き出した系列のラベルと真のコンセプトが、同じデータ・seedのFedHASPのrun（両方の間隔）の記録と全標本で一致しなければ止める。
- 手法（Riverの既定の値、river 0.27.0）: ARF（`forest.ARFClassifier`）、SRP（`ensemble.SRPClassifier`）、Leveraging Bagging（基本はHoeffding木）、Hoeffding Adaptive Tree、DWM（Kolter & Maloof 2007のアルゴリズム1を実装。β=0.5、θ=0.01、p=1）。
  - DWMの基本の学習器はHoeffding木にした。元論文はNaive Bayesと決定木を使うが、RiverのGaussianNBは画素をそのまま入れたMNIST4で単独でも当て推量に近い精度（手元、最初の1500標本で0.113）になり、DWMも0.106だったため。
  - CPF・RCDなど再来するコンセプトの専用の手法は、Riverに無い。この段階では入れない。
- 手元の確認（2026-11-17）:
  - 書き出した系列のラベルと真のコンセプトが、別に実行した製品のrun（SINE2・1000標本・seed 0と、MNIST4・5000標本・seed 0・コンセプトの変化5回。fedsda系の構成、fedavg、FedDriftのOracle、間隔50と1000／5000）の記録と全標本で一致した。
  - SINE2・SEA2×間隔50・1000×seed 0〜2、1000標本で、予備実験の6構成・Oracle・書き出し・River（WSL）・集計が最後まで通った。
  - Riverは、Windowsではアプリケーション制御がnumpy・Riverの拡張のDLLを止めるので、手元ではWSL（Ubuntu）で動かした。
  - MNIST4・seed 0の1 runの時間（WSL）: ARF 8秒、Hoeffding Adaptive Tree 37秒、Leveraging Bagging 44秒、SRP 52秒、DWM 9秒。書き出しは1件17秒。
- 解釈の限定（結果を書くときに必ず添える）:
  - 基本の学習器と学習の量が違う。FedHASPは、事前学習した神経網（共有の特徴抽出器と、コンセプトごとのアダプタ。事前学習は複数のepoch）を使い、標本ごとに32件のミニバッチで更新する。Riverの手法は、生の特徴を入れた木（DWMも木）を使い、事前学習の標本は1回ずつ学習するだけ。差には、ドリフトへの対応の仕方だけでなく、学習器と学習の量の違いが混ざる。とくにMNIST系の画像では、木は神経網より不利になりうる（手元のMNIST4・seed 0で、FedHASP 87.7%に対し、Riverの手法は38〜67%）。ドリフトへの対応の仕方だけの差を見るには、同じ神経網を基本の学習器にした比較手法（例: DWMの専門家を神経網にする）が要る。これは未実装。
  - 経過時間は、PythonのRiverとPyTorchのFedHASPの比較なので、計算資源の比較には使わない。
  - 特徴の数値の精度: FedHASPは特徴をfloat32にして学習し、Riverはfloat64のまま使う。MNIST系の画素は同じ値になるが、SINE・SEAなどは丸めの差が残りうる。精度への影響は小さいと見込むが、確かめていない。
  - 95%区間はセルごとで、多重比較の補正はしていない。「多くのセルで有意」とは書かない。
- 独立レビュー（2026-11-17）: GPT-6 Lunaは利用上限で使えなかった（`codex exec`が「usage limit」で終了）ので、Claude Haiku 5.5（effort medium、読むだけ、session `221ab7aa-8c35-42d0-a93b-e2b5a748b344`、`is_error=false`、`modelUsage`はclaude-haiku-5-5）に依頼した。判定FAIL（実装のMajor 1件）。採否:
  - 採用（Major）: 入力の照合がFedHASPの1構成だけだった。全構成とOracleの全runへ広げた。SINE2・SEA2の小さい条件で84組が一致し、ラベルを1つ変えた系列で`fedsda-single-model-prediction`の不一致として止まることを確かめた。
  - 採用（報告の限定）: 基本の学習器と学習の量の違い、経過時間の比較の限界、数値の精度。上の「解釈の限定」に書いた。
  - 不採用: 「FedHASPは集約の間隔ごとにしか学習を反映しない」という指摘。製品の既定は、警報の標本を除く標本1件ごとに学習の要求を記録し、要求1件ごとに、そのモデルの学習標本から32件のミニバッチで1回学習する（`fedsda_final_configuration_run_settings.py`の`_TRAINING_REQUESTS_PER_UPDATE_INTERVAL = 1`。集約の時点の`flush_pending_local_updates`は残った要求を処理するだけ）。ただし標本は帰属の保留（FIFO 30件）を経てから学習データに入るので、学習データへの反映は最大30標本遅れる。
  - 採用（Minor）: 書き出しの再開はNPZとJSONの両方がそろったときだけ飛ばす。来歴のファイルは呼び出しごとに時刻つきの名前で残す。系列の対応のキーに標本数を足す。未使用の変数を消す。区間に多重比較の補正が無いことを集計の出力に書く。DWMで予測がNoneのときの扱いをdocstringに書いた。
  - 修正の後に主担当が入れた不具合（来歴のファイルの名前を変えたため、集計がそれを系列の記録として読もうとした）を見つけて直し、小さい条件で集計が通ることを確かめた。実装のMajorの修正なので、同じ担当（Haiku 5.5、effort medium、読むだけ、session `0bb5346b-0c75-45a0-8de1-2b453f81f71f`）に修正箇所の再確認を依頼し、PASS（Majorは解消、新しいBlocker・Majorなし）。不採用の根拠も妥当と確認された。再確認のMinor 4件のうち、系列の記録の長さの検査、欠けの検査を照合より先にすること、系列の記録のJSONを一時ファイルから置き換えることを直した。`--streams`だけでの照合はしない（`--river`と組）と docstringに書いた。上の不採用の文言も、再確認の指摘に合わせて正確にした。

## 結果（2026-11-17、主担当）

- 実行: uranium、`results/fedhasp-single-client-pilot-v16/20261117_101402_single-client-seeds0-29`（6構成、3,600 run、失敗0、commit `343c95f9`、140 workers、約2時間3分）と`20261117_122212_oracle-single-client-seeds0-29`（Oracle、600 run、失敗0）。段階2（River）は、uraniumのPython 3.10でriver 0.27.0が入らず未実行。
- 集計: `python -m tools.research_single_client_stream_baselines.analyze --pilot ... --oracle ... --output results/fedhasp-single-client-pilot-v16/analysis-pilot`（`analysis_single_client.md`・`cells.csv`・`accuracy.csv`）。全構成で組の欠け・余分なし。run単位の経過時間はログを保存していないので無い。
- 連合学習（10 client、seed 0〜9、間隔50／500）の値と並べる（pp。1クライアントは30 seed、間隔50／5000、括弧は95%区間）:

| 効果 | 連合学習 50／500 | 1クライアント 50 | 1クライアント 5000 |
|---|---|---|---|
| 学習を固くする（混合の予測） | +0.63／+0.30 | +0.07 [−0.08, +0.23] | −0.06 [−0.18, +0.06] |
| 学習を固くする（現在のモデルだけの予測） | +0.78／+0.80 | +0.27 [+0.12, +0.41] | +0.25 [+0.11, +0.38] |
| 予測を混ぜる（固い学習） | +1.97／+1.16 | +0.99 [+0.93, +1.04] | +0.12 [+0.04, +0.20] |
| 予測を混ぜる（柔らかい学習） | +2.12／+1.66 | +1.18 [+1.11, +1.26] | +0.43 [+0.32, +0.53] |
| 2つの版を混ぜる（FedHASP−局所のパラメータだけ） | — | +0.65 [+0.62, +0.69] | 0.00（全run一致） |
| Oracle−FedHASP | +0.41（2間隔の平均） | +0.91 [+0.75, +1.08] | +0.47 [+0.36, +0.57] |
| FedHASP−単一のモデル | — | +8.57 | +7.81 |

- 純度: 固い0.860（間隔50）・0.894（5000）、柔らかい0.829・0.846（全部を1モデルに入れた基準0.562）。柔らかい学習は純度を下げるが、混合の予測では精度は変わらない。
- 間隔5000では、FedHASPと`fedsda-local-parameter-prediction`の精度が全run（300）で一致した。集約が無いと、同期の時点の版が使われず、2つの版の混合が働かない。間隔5000のFedHASPが「統合も版の混合も無い」1クライアントの形になる。
- まとめ（数値をそのまま述べる）: 1クライアントでは、混合の予測のもとで学習を固くする効果は0と区別できない（連合学習では+0.63／+0.30）。予測を混ぜる効果も、純粋な1クライアントの形（間隔5000）では+0.12と小さく、間隔50の+0.99のうち+0.65は2つの版の混合の分。固い割り当てと混合の予測の効果は、連合学習の設定で大きく出る。連合学習との条件の違い（client数、seed、間隔、学習データの量）があるので、連合学習が効果を大きくする原因（集約で割り当ての誤りが広がるなど）は、この比較だけでは特定できない。
