# IMPROVE-019. クラスの支持数と対損失差を用いて候補を検証する

- 記録日: 2026-10-17。種別: アルゴリズム調整。状態: 未検証・未採用。
- 基準: `9ea1107`、混合予測/FIFO30/共通T120。候補検証診断で発見、実装specは未作成。
- 対象: `methods/fedsda/candidate_model_selection/post_alarm_candidate_loss_evaluation.py`ほか検証の継続・解決経路。

## 事実と仮説

現在は将来10件を5件ずつに分け、両方で損失改善を要求する。それより先に、履歴平均を0.1超えて悪化していない既存参照を優先する。
MNISTの保存判定は10件に平均約6.5クラスしかなく、真変化対応の判定でも、片側に変化した数字が来ない場合がある。
履歴優先によって、両区間で候補の損失が小さくても却下される例も確認した。
このことは却下候補の真の有用性を証明しない。[診断の詳細](../fedsda-candidate-validation-diagnosis-20261017.md)。

## 案と懸念

警報の起点になった観測クラス等の支持数と、同じ到着標本での候補対既存の損失差を蓄積する。
現行も同じ標本を両者で評価する対比較であり、対比較そのものを新しく導入する案ではない。
全クラスの平均だけで少数クラスの変化を薄めず、他クラスの悪化も監視する。
既存が履歴許容内でも、候補に十分な改善の証拠があれば採用可能にする。
固定5+5の分割を緩める場合も、期限・不十分時の処理・継続観測による判定の偏りを設計する。

検出に用いたデータで再び判定して確証と扱わず、候補学習後の標本で比較する。
警報が全体損失由来の場合や希少クラスでは支持が集まらず、待ち時間・メモリ・誤採用が増える可能性がある。
実行時に真の概念や「ラベルが変わった数字」を知っている前提は置かない。

## 必要な検証と判断

履歴優先の除去と比較参照選択の変更を含む対照は、この案全体の検証ではない。
クラス別の支持、採用/却下、検証時間、変化後精度、非変化クラス、モデル数・通信・計算を複数seedで比較する。
改善対象seedを最終評価と呼ばない。数値・選択・待ち時間が変わるため採用時は別specと動作基準が必要。
変更commit: なし。
