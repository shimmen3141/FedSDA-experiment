# IMPROVE-003. 固定した参照モデルの検証損失を規定件数の到達時にまとめて評価する（候補・未検証）

種別: 計算効率。旧実装の固定基準: 748c3aa。発見spec: post-alarm-candidate-validation-sample-observation（2026-10-07、記録は2026-10-08）。損失の値が浮動小数の丸めの範囲で変わる可能性があり、挙動を完全に維持する整理とは言えない。

- 記録日: 2026-10-08。対象は旧clients/fedsda.pyの_observe_forward_validation、移植済みのruntime/post_alarm_candidate_validation_sample_observation.pyのobserve_post_alarm_candidate_validation_sample。
- 確認した事実: 警報後の検証では、到着した標本ごとに候補1件と固定した参照モデル全件をそれぞれforwardして損失を記録する。forward回数は（検証標本数）×（1＋参照モデル数）。最終構成のforward_persistentでは参照モデルは警報時点の値で固定され、検証中に更新されない（参照specとsession開始specのtestで、候補を継続更新しても参照が不変であることを確認している）。候補は検証中も更新されるので、候補の損失は標本の到着時点で評価する必要がある。
- 確認した事実（適用外）: 参照も学習させる方針（旧shadow_tournament）では参照が検証中に更新されるため、この案は適用できない。この方針は移植しないと決めている。
- 変更案: 参照モデルの損失は標本を保持しておき、規定件数へ到達した時点（または終端回収の時点）で、参照モデルごとに1回のバッチforwardで評価する。候補の損失は現状どおり標本ごとに評価する。
- 期待する利点（仮説）: 参照のforward回数が（検証標本数）×（参照モデル数）から（参照モデル数）へ減る。保有モデル数が多い条件ほど効果が大きい。実際の時間削減量は未測定。
- 悪化・トレードオフの懸念: バッチforwardと1件ずつのforwardで損失が丸めの範囲で異なる可能性があり、参照間の順位が同率付近で入れ替わると採否が変わりうる。検証標本を到達時まで保持するメモリが必要（検証標本は現在も保留標本として保持しているので、追加は小さい見込みだが未確認）。未到達で終わるsessionでは参照の評価結果を使わないため、評価自体を省ける。計算量診断（旧compute_countersのdetection計上）の値と計上時点が変わる。
- 必要な比較: 1件ずつとバッチの損失の差の大きさ、採否・選択された参照IDの一致率、全体runの指標（精度・モデル数・切替数）、検証区間の計算時間。完全一致を採否基準にするか、指標の分布で判断するかは未定。
- 現在の扱い: 未検証・未採用。リファクタリングでは旧と同じ標本ごとの評価を維持する。採用する場合は別specで診断・回帰基準の扱いを承認する。
