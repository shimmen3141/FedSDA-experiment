# IMPROVE-009. 依存境界testの方式を一本化し、機械生成の注入契約testを減らす

- 記録日: 2026-10-09。種別: 簡略化（testの保守）。状態: 見送り（2026-10-09ユーザー決定。行う場合の条件を下に記す）。
- 対象: `tests/refactoring/test_single_run_dependency_boundaries.py`（基点commit `caa5b8d`）。発見の経緯: 手順の簡素化の検討。

## 確認した事実

- 10,616行、test関数44、条件3,043（全pytest約10,000件の約3割）。moduleごとに名前の組で許可集合を書いた分岐が58、別形式の分岐が10。
- 条件の多くは、許可するsymbolごとに5通りの書き方（そのまま・別名・module全体・private・star）を機械的に並べたもの。拒否の3通りは、symbolによらない共通の仕組み（許可集合にない名前は拒否）を通るだけで、許可の2通りは、実際のsourceがそのsymbolをimportして全体の依存testが通ることで確かめられている。
- 検査の方式がmoduleの群によって違う（import文を名前へ直す方法、`__future__`の扱い）。「許可集合と実際のimportの一致」を1件で確かめる形へ移すには、群ごとに方式を読み解く必要がある。機械的に当てると58のうち51が見かけ上不一致になった。

## 案

許可集合をdataとして1箇所へ登録し、方式を1つにして、「許可集合＝実際のimport」を全moduleで1件のtestで確かめる。symbolごとの注入契約testを消す。

## 見送りの理由

移行の負担（通常のspec 1〜2個分と見積もった。未計測）に対して、検出できる不具合は増えない。testの実行は数秒。得られるのは、fileの大きさと件数の削減、依存を変えるときの修正箇所の削減だけ。

## 代わりに行ったこと

- 新しいmoduleには、symbolごとの注入契約testを足さない（共通引継ぎ手順）。
- 移行なしで入れられる検査「許可集合の各名前が実際にimportされている」を全moduleへ入れた（spec shared-verification-infrastructure）。

## 行う場合の条件

次のどちらかになったら再検討する: (1)移植が終わり、moduleごとの厳密な許可集合が不要（層ごとの規則で足りる）と判断できる。この場合は移行でなく削除になる。(2)依存testの保守（修正箇所の多さ、fileの大きさ）が実際に作業の妨げになった。時間が経っても移行の作業量そのものは減らない。
