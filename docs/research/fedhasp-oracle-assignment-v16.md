# FedHASPの固い割り当てを真のコンセプトに合わせた診断（FedHASPを土台にしたOracle、基準版16、計画 2026-11-01）

- 目的: FedHASP（基準版16）の固い割り当て（警報の時期・帰属先・統合）を、決めた規則で真のコンセプトに合わせたときの精度を測る。(1) 固い割り当ての誤りで失っている精度、(2) その内訳（警報の時期だけを合わせた分と、帰属先・統合まで合わせた分）、(3) FedDriftを土台にしたOracle（製品の構成`feddrift-oracle-concept-assignment`）との差（割り当てが真のコンセプトに合っているときの、柔らかい予測と標本ごとの学習の寄与）を示す。論文の5.5節（固い割り当ての分析）の診断に使い、比較手法の表には載せない。
- 背景: 2026-11-01のユーザー判断。基準版13のときにSEA2・SEA4だけで同じ診断をし、Oracleが+1.1〜+1.8pp上だった（[IMPROVE-030](improvement-candidates/improve-030-split-partially-changed-concept-on-client.md)の2026-10-27の節）。
- この文書が計画の正本。末尾の「レビューの経緯」は記録だけ。

## 使う研究ツールと3変種

既存の`tools/research_oracle_concept_assignment`（基準版13のときに作成）。製品の構成`fedsda`をそのまま動かし、実行中だけ次を差し替える。2026-11-01に、基準版16の製品（`7874c449`）の上で既存の検査17件が通ることを主担当が確かめた。

- `product-default`: 差し替えなし。製品の`fedsda`と全記録が一致することを既存の検査`test_default_entry_matches_direct_product_all_records`が確かめる。
- `product-default-oracle-change-alarm`（警報だけOracle）: 監視器の合図を使わず、clientごとに、真のコンセプトが変わった標本を1標本目として5標本目で警報とする。2つの変化が5標本以内に来たら、既存の実装は例外で止める（`policy.py`の`_ConceptChangeAlarm.observe`。本規模のデータの予定は変化の後300標本は次の変化を起こさないので、起きない）。警報の後の帰属先の選択（製品のMDL）と統合は製品のまま。
- `product-default-oracle-concept-assignment`（Oracle）: 警報は上と同じ。警報の後の選択の結果を、変化区間＝5と、次の帰属先に置き換える。帰属先は、そのclientの割当の記録（`model_training_and_assignment_counts_store`）で、そのclientが割り当てた学習標本の多数派のコンセプト（同数は多数派なし）が、警報の標本の真のコンセプトと同じ保有モデル（複数なら割り当てた標本の多いもの、同数なら製品の保有の順で先）。それが現在のモデルなら「現在のモデルのまま」、ほかのモデルなら「保有モデルへ」、無ければ「新しいモデル」。新しいモデルの候補の学習・採用は製品の規則のまま（学習者の名前は製品の計算の結果を使う）。統合は、クラスタリングの対の判定の値を、多数派のコンセプトが同じ対だけ統合する値に置き換える。ほかの部品（モデル、学習、予測の混合、通信、監視器の計算）は製品のまま。

## 論文での説明の限定

このOracleは「決めた規則で固い割り当てを真のコンセプトに合わせた診断の条件」であり、割り当ての最良の値や精度の上限ではない。論文では次を書く。(1) 警報は変化から5標本目で、直後の4標本は前のコンセプトの扱い。(2) 帰属先はそのclient自身の割当の記録で決めるので、そのclientが一度も割り当てていないコンセプトのモデルは、ほかのclientが学習していても帰属先にならず、新しいモデルが作られる（後の統合で、多数派のコンセプトが同じモデルどうしは統合される）。(3) 候補の学習と採用、予測、学習は製品のまま。基準版13の結果では、Oracleは新しいモデルの採用が多く、通信・計算が増えたので、費用は比較の対象にしない。
