# LEGACY-021: クラス別の正誤の判定が、違いの証拠が閾値に届かないと、違う概念のモデルを統合する

- 発見日: 2026-10-22。対象: `src/federated_learning_experiments/methods/fedsda/consolidation/model_clustering_calculations.py`の`compute_classwise_unique_correctness_decision_score`（旧の`class_functional_confidence`を移植したもの）と、判定の値の閾値0.1、対の評価の標本の最小数`_MINIMUM_PAIR_EVALUATION_SAMPLE_COUNT = 5`（`runtime/fedsda_final_configuration_run_settings.py`）。発見の経緯: 初期モデルの統計を交差検証で取る変種（[LEGACY-020](legacy-020-optimistic-initial-model-loss-statistics.md)）で、MNIST4・間隔100・seed 9の精度が下がった原因の調査。
- 種別: 旧から引き継いだ判定の弱点。状態: 未対応（2026-10-22に記録）。

## 内容

判定の値は、クラス別の「片方のモデルだけが正解した割合」の、同時信頼下限（Wilson、信頼水準0.95、Bonferroni補正）の最大。0.1以下なら同じクラスタにする。信頼下限は、片方だけが正解した件数が0なら、評価の標本数に関わらず0になる。標本数が下限（5件）以上のクラスが無ければ、全体の件数を使う。

この判定は「違いの証拠が十分にあるときだけ、別のモデルとして残す」形なので、評価の標本が少ないと、違う概念のモデルでも、違いの証拠が足りずに統合される。

## 起きた場面（手元、Windows、基準版10の既定＋初期モデルの統計の交差検証）

MNIST4・間隔100・seed 9（各5000標本・10 client、精度91.97%。同じ条件の既定は94.34%）の40回目の同期で、違う概念のモデル0と1を、判定の値0.0で統合した。そのときの入力（Git管理外の一時scriptで記録、`results/fedsda-provisional-candidate-expert/20261022_mnist4-cross-validated-initial-statistics-diagnosis/merge_inputs_seed9.json`）は、評価した標本が全体で28件、片方だけが正解したのは1件（小さいIDのモデルだけ）。クラス別は10クラスで1〜5件ずつ、5件以上のクラス（2つ）では、片方だけが正解した件数が0。統合の後、モデルは3つ（MNIST4の概念は4つ）のまま、後半の精度が既定より4〜6pp低いままだった。

既定の同じseedでは、この統合は起きない（序盤の軌跡が違い、40回目の同期の場面に入らない）。交差検証が原因ではなく、軌跡が変わったことで、この弱点が表に出たとみる。

記録の表`model_pair_clustering`（真の概念が同じか、同じクラスタにしたか、判定の値）と、`client_cross_evaluation`（両方向の、正誤を比べた評価の標本数の合計を、対の評価の標本数とした）を突き合わせた（Git管理外の一時script）。

（SEAは、概念どうしが機能の上でほとんど区別できないので、違う概念の統合が多くても精度への影響は小さい）

- 既定でも、違う概念の統合はMNIST4の40 runのうち11、CIRCLE2の9、MNIST2の8で起きる。その対の評価の標本数は、ほとんどが約100件（同じ概念の対の統合と同じくらい）で、上の28件のような、標本が少ない場面に限らない。判定の値は0ではなく、0.05〜0.08（閾値0.1の下）。評価の標本（約100件）が10クラスに分かれ、片方だけが正解するクラス（概念の違いが表れるクラス）の件数が少ないと、信頼下限が閾値の下に収まる。
- 違う概念の統合が起きたrunの精度は、起きなかったrunより低い条件がある（同じ条件の10 seedの中で比べた平均。因果は未確認）: MNIST4・500で90.86％（8 run）対92.00％（2 run）、MNIST4・200で92.89％（3 run）対93.40％（7 run）、CIRCLE2の4間隔で0.23〜0.42pp低い。MNIST2では差が無い（−0.07〜+0.23pp）。
- したがって、この記録の弱点は「評価の標本が少ない場面」より広く、「違いの証拠が閾値の位置に届かないと統合する」判定の形そのもの。
- 統合の時期（2026-10-22、同じraw）: 統合（吸収）は、同じ概念の対でも違う概念の対でも、ほとんどが吸収されるモデルの登録の直後の最初の同期で起きる（違う概念の対: SEA4 113/117、MNIST4 11/14、CIRCLE2 8/11）。判定は、実質的に、登録したばかりのモデルについて1回だけ行われ、そのモデルはまだ短い区間でしか学んでいない。SEA4では、この統合が、概念2が専用のモデルを持てない主な経路だった（[NEW-006](new-006-minimum-description-length-keeps-partially-changed-concept-in-current-model.md)の「概念2がどこで取り込まれるか」）。

## 直す方法の案（未検討）

- 統合の向きの検定にする: 「片方だけが正解した割合」の信頼上限が閾値より小さいとき（同じであることの証拠があるとき）だけ統合する（同等性の検定の形）。証拠が足りない対は、統合しない。閾値0.1は残る。
- 評価の標本の最小数を、判定の値の信頼区間の幅が閾値を下回る数にする（標本が足りない対は統合しない）。
- クロス評価の標本を増やす（今はclientあたり最大50標本）。通信と計算が増える。
- 判定の値・閾値の局所的な調整ではなく、統合の時期・証拠・操作を作り直す4つの方向を、[IMPROVE-028](../improvement-candidates/improve-028-evidence-accumulating-model-consolidation.md)に記録した（2026-10-22）。

## 基準版12での頻度と時期（2026-10-26、`results/method-comparison-v12/fedsda`のMNIST4の40 run のraw）

記録の表`model_pair_clustering`（真の概念が同じか、同じクラスタにしたか）と、標本ごとの予測の正誤を数えた（Git管理外の一時script）。

- 違う概念の統合が起きたrunは40のうち4（間隔100・seed 2、間隔500・seed 4——5回——、間隔500・seed 9——2回——、間隔50・seed 0）。合わせて9回で、**全部がrunの前半**（同期の回数の、最初の4分の1に6回、次の4分の1に3回）。登録が多いのは、概念が初めて現れる前半なので、統合の判定の機会もそこに集まる。
- ある概念の精度が88%を下回ったrunは40のうち1（間隔500・seed 7、85.2%）。このrunでは違う概念の統合は記録されていない（一部だけ変わる概念が、専用のモデルを持てずに取り込まれた形——NEW-006——とみる。未確認）。最後の4分の1の標本でも84.3%で、run の中で回復しない。
- 判断: 基準版12でも、崩れ（違う概念の統合、一部だけ変わる概念の取り込み）は、頻度は減ったが起きる。違う概念の統合はrunの前半に集まるので、標本数の多いrunでも、起きる回数がrunの長さに比例して増えるとは限らない。一方、起きたときの損は取り消せず（統合）、回復しない（取り込み）ので、長いrunでは、損が続く期間が長くなる可能性がある。標本数を増やしたrunでの頻度と、損が続く長さは、未確認（確かめるなら、MNIST4を各client 10000〜20000標本で数seed流し、同じ数え方をする）。
