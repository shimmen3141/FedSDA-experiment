# リファクタリング方針案

2026-10-02時点のコードを調査した方針案。開始点は`748c3aa`。
この文書は設計・移行方針を示すもので、コードの移動やリネームはまだ行っていない。
後続のユーザー指示を反映し、新実装には旧名alias・旧形式読込み・旧import窓口を残さない方針とする。

## 1. 目的と判断基準

最終Residual Adapter＋Switching構成と比較手法について、処理を追いやすく、
一つの機能の変更が他の機能へ波及しにくい構造にする。
実装の責務、依存方向、名前の意味、変更時の検証範囲を明示する。

- 一つのモジュールには、一緒に変更する理由のある処理を置く。
- 状態には所有者を一つ決め、他の機能が直接書き換えることを避ける。
- 上位の実験実行が具体的な方式を組み立て、計算・判断部は実験実行や保存処理へ依存しない。
- データ型、入出力、更新する状態、処理の順序を、小さな境界ごとに定義する。
- インターフェースは実際に差し替える箇所に設ける。各関数のために抽象クラスを増やさない。
- 名前は役割・判断基準・時間的な意味を表す。短さより、意味の明確さ・他の概念との区別・実態との一致を優先する。
  必要なら4語・5語以上を使う。単語数を増やすことや小さいファイルを目標にしない。

同じGit履歴の専用ブランチを、別ディレクトリのworktreeへcheckoutして進める。
旧実装は`748c3aa`で固定した参照として保持し、新worktreeでは新しい構成・API・設定形式を段階的に実装する。
必要な計算処理は検証しながら移植し、旧名や互換分岐は新しい実行経路へ持ち込まない。
worktreeは別のcheckoutを用意する機能で、旧コードが自動で消える機能ではない。
新ブランチの最終状態から旧構成を除き、旧実装の保守と新実装の保守を二重に続けない。

## 3. レイヤーと配置の案

以下は新実装の配置案で、各ディレクトリは対応する責務を実装した時点で作る。
ルートパッケージ名は2026-10-02にユーザーが承認した`federated_learning_experiments`とする。
扱う対象と用途を表し、個々の手法名やpreset名から区別する。以下の下位配置は設計候補である。

```text
src/federated_learning_experiments/
  core/                 # ID・状態・イベント・機能境界の小さな型
  learning/
    models/             # モデル構造、共有部、概念固有部
    training/           # ローカル更新、共同学習、勾配統合
  methods/
    fedsda/
      client.py         # 1サンプルの進行を組み立てる
      server.py         # 同期ラウンドの進行を組み立てる
      detection/        # 全体/クラス別の損失監視
      routing/          # 予測重み、activation、集約後再較正
      assignment/       # 既存モデルへの適合・データ帰属
      model_creation/   # 候補学習、前向き検証、採否
      consolidation/    # 対評価、クラスタ作成、統合・共有
    feddrift/           # FedDrift固有の進行・隔離・同期
    oblivious/          # 無適応baseline
  data/                 # 既存の生成・読込み・概念スケジュール
  configuration/        # 実験設定の解決・検証、方式定義、preset。機能固有の型は各機能へ
  experiment_spec/      # 掃引、指標・保存契約の宣言
  runtime/              # 具体方式の組立、stream進行、実験・掃引の実行
  evaluation/           # 指標計算、診断、履歴からの集計
  artifacts/            # 新schemaのCSV/NPZ/manifestの読書き・復元
  visualization/        # 結果からの描画
```

`core`を便利関数の寄せ集めにしない。各機能だけで使う型はその機能の近くへ置く。
サーバ/クライアントという配置と、検出/routing等の責務別配置を組み合わせる。
shared backboneやResidual Adapterはモデル・学習方式であり、独立した通信手法名として扱わない。

### 依存方向

- `core`はruntime、成果物I/O、個別手法へ依存しない。
- `learning`と各手法の計算・判断部は、必要な型と明示的な設定を受け取る。
- `runtime`は構成を解決し、具体的なモデル・検出器・判断方式を生成する。
- `evaluation`は観測記録を読み、`artifacts`は結果を保存する。
- `visualization`は結果を読み、手法内部の可変状態を参照しない。
- CLIと`tools/`は構成と実行・保存の窓口を呼び、アルゴリズムを実装しない。

`configuration`・`experiment_spec`の宣言と`artifacts`の読書きを区別し、schemaがファイルI/Oへ依存しないようにする。
手法の計算部には必要な機能固有の設定を渡し、汎用の選択肢一覧・preset解決へ依存させない。
実際の循環参照は移行対象ごとに確認し、この案を調整する。

### 採用するアーキテクチャ原則

クリーンアーキテクチャの依存方向、ヘキサゴナルアーキテクチャの差し替え境界、
機能別配置、計算と副作用の分離を組み合わせる。
方式の組立を外側へ置き、手法の判断部がCLI・保存・描画を参照しない。
検出器・routing等の実際に差し替える箇所へ小さなインターフェースを設ける。
モデル・学習層ではPyTorch依存を明示し、単純な関数まで抽象クラスで包まない。
状態を持つ監視・routingには所有者と更新時点を定める。

## 4. 最初に明確にする機能境界

| 機能 | 所有する状態・責務 | 境界で受け渡すもの |
|---|---|---|
| 予測routing | expert重み、ラベル観測前の混合予測 | 予測スコア、expert ID、観測後のexpert損失 |
| データ割当 | 現行割当先、帰属保留FIFO、概念別ストア | 帰属確定標本、割当変更 |
| 損失監視 | 全体・正解クラス別の検出器状態 | 割当モデルの損失、警報、推定変化点 |
| 候補検証 | 検証session、候補・比較用モデル、前半/後半の損失 | 採否判断、採用モデル、適用する割当変更 |
| ローカル学習 | optimizer、共有部と固有部の更新 | 確定データ、更新モデル、実行件数 |
| サーバ同期 | global ID登録、集約、配布の順序 | upload、集約結果、ID対応表 |
| モデル統合 | 対評価、linkage、統合判断 | クラスタ、統合結果、旧新ID対応 |
| 診断 | 観測記録・計数・oracle等の補助評価 | 実行側からの観測。予測・学習の判断へ返さない |

クライアントは順序を管理する。routingや候補検証がクライアント全体へアクセスする構造を避け、
必要な値と限定した操作を渡す。新しい戻り値・記録形式を境界ごとに定義する。

`predict`と`observe_label`を分け、呼出し側がラベル観測の前後を明示できるようにする。
大量のイベントバスや汎用plugin機構の導入は、この分離の前提にしない。

## 5. 命名の方針と具体候補

用語を先に小さな対応表へまとめる。model、expert、assignment、leader、candidateを区別する。
`sample_index`、`round_index`、`client_id`、`model_id`を使い、単位が重要な数値は
`sample_count`、`parameter_count`、`byte_count`などを明示する。
`get_*`は状態を更新しない取得、`observe_*`は標本の観測、`update_*`は更新、
`evaluate_*`は判断材料の計算、`apply_*`は決定済み変更の適用に使う。

| 現在の名前 | 問題・意味 | 候補・対応 |
|---|---|---|
| 長いmode名 | 各軸が混在し、名前だけでは最終構成が決まらない | preset `fedsda_switching`＋明示的な構成。新APIは新名に統一 |
| `RestartingSoftRouting` | 割当変更時resetと予測方式の選択が混在 | `prediction_routing_strategy`と`routing_reset_on_assignment_change_policy`へ分ける |
| `SOFT_ROUTING_CONTEXT` | `switching`や`meta_switching`は単なる文脈ではなく予測方式 | 内部設定を`prediction_routing_strategy`へ。クラス別文脈は別概念として定義 |
| `current_model_id` | 現行予測モデルと誤読されるが、最終混合予測のleaderとは別 | データ・損失監視の文脈では`assigned_model_id` |
| `ProtectedSoftRouting` | 何を保護するか不明 | `CumulativeLossGatedPredictor`等。累積損失による混合採用条件を表す |
| `forward_persistent` | 既存モデル再適合・現行優先・前半/後半の検証が名前から見えない | 内部は既存`ForwardCreationPolicy`の規則を活用。表示は「再適合比較付き二分区間前向き検証」 |
| `ClassESR` | 正解クラス別だけでなく全体も監視 | 説明用語を「全体・正解クラス別e-SR監視」へ。内部は検出器と監視範囲を分離 |
| `_train_heads_together` | Residual Adapterや共有部まで更新する | `train_experts_jointly`等。共有部更新の有無は引数/設定で表す |
| `_record_prediction` | 予測・更新も実施する | `predict_with_experts`、`observe_expert_losses`、`record_prediction_diagnostics`等に責務を分割 |
| `_save_raw_run` | 内部状態収集と保存を一体化 | `collect_run_trace`と`write_run_npz`等に分ける |

候補名は実装単位の設計時に確定する。関数を改名して意味の混在を残すことは避ける。
`SwitchingExpertRouter`や`ResidualConceptAdapter`など、実態を表す既存名は維持してよい。
FedSDAという研究手法名の変更は別の研究判断として扱い、内部整理の前提にしない。

### 新実装の名前と過去成果物

新実装のPython API、CLI、preset、設定、CSV列、NPZ keyは新しい用語に統一する。
旧名alias、旧設定の自動解釈、旧import窓口は設けない。未定義の項目は明確なエラーにする。
新manifestにはschema versionを付け、未対応のversionを黙って受理しない。

過去成果物は元の名前・来歴・hashのまま保存する。旧実装の固定環境で解析するか、
必要な結果だけ別の移行作業で新形式へ明示的に変換する。
変換物には元成果物の場所・hashと変換内容を記録し、元成果物を上書きしない。
旧形式の変換処理が必要になっても、新実装の通常実行・通常読込みの依存にはしない。

goldenとの比較もテスト用の明示的な対応表で行う。旧APIを本体に追加する理由にはしない。
新しいID・key名への対応付けと、精度・通信・計算量・イベント順序等の挙動比較を分ける。
旧goldenは保存し、値の差を新しい名前への変更として隠さない。

## 6. 最終提案と代替方式の整理

最終構成、主要ablation、比較baselineは分かりやすいpresetとしてまとめる。
移植する選択肢は、最終提案・論文用比較・今後の研究に必要な範囲を先に一覧化して決める。
Meta-switching、Cached、PCGrad等は必要性を個別に判断する。旧実装に存在する全選択肢の再実装を必須にしない。
採用しない選択肢は旧実装と成果物へ保存し、新APIに名前だけの選択肢や互換分岐を残さない。

組合せごとの多重継承を増やす方式から、検出・routing・学習・作成・統合の構成による方式へ移行する。
既存`MODE_SPECS`は実体生成、OptionSpec等は能力・制約という責務を明確にし、
手法の対応情報を文字列分解と複数の独立した表へ散在させない。
既存`ExperimentConfiguration`の考え方を活用し、新設定を不変の型付き値として定義する。
新実装の計算部はグローバル`config`を参照せず、必要な設定を引数で受け取る。

### オプションを追加・削除しやすくする設計

レイヤー分けに加えて、機能ごとの設定と構成の組立を分離する。

| 要素 | 管理する内容 |
|---|---|
| 機能別の設定型 | その機能の項目・型・単位・既定値・値の範囲 |
| 選択肢の定義 | 正式名、説明、必要能力、組合せ制約、所属する設定型 |
| runtimeでの組立 | 検証済み設定から具体的な実装を生成する対応 |
| 実装 | 小さなインターフェースを満たす計算・判断・状態更新 |
| preset | 選択肢と固定値の組合せ。実装や条件分岐は持たない |

例えばrouting設定は、予測方式・有効化方針・再較正方針等に分ける。
特定方式だけが使う値は、その方式の設定型へ所属させる。
無関係な方式の値を全方式共通の巨大な設定オブジェクトへ追加し続けない。
各機能の選択肢定義を集約し、CLIのchoices、参照文書、掃引可能な項目、設定の保存表現を導出する。
具体的な実装をimportする組立処理は上位のruntimeに置く。

設定の解決順は、preset展開→明示指定の反映→値・組合せ検証→実効設定の確定→実体生成とする。
未使用・未対応の指定を黙って無視せず、どの項目がどの条件で不適切かを説明する。
保存する条件は実効設定から生成し、runの途中で変化させない。

追加時は、担当機能の設定・選択肢定義・組立対応・実装・必要なテストを変更する。
複数のmode名一覧や巨大クライアントの独立した条件分岐を毎回修正する構造を避ける。
新しいアルゴリズムには実装と検証が必要であり、登録一行だけで対応できることを目標にしない。

削除時は、選択肢登録・実装・専用設定を除き、関連preset・掃引計画・テスト・文書も更新する。
存在しない選択肢、未登録パラメータ、参照先のないpreset、生成できない選択肢を整合性検査で検出する。
旧名を受理するaliasは残さない。必要なら変更内容と新しい指定方法を移行記録へ残す。

## 7. 移行の順序と完了条件

実装順序と依存方向は別に判断する。最初に機能境界・状態所有者・必要な設定を整理し、
最終構成に必要な設定と検証から、小規模な一実験の実行経路へ接続する。
選択肢カタログ、preset、保存表現等の汎用基盤を全て完成させてから移植する順序にはしない。
比較手法・ablationの移植に合わせて汎用部分を整え、実際に必要な差し替えを確認する。

| 段階 | 変更の単位 | 完了の証拠 |
|---|---|---|
| 1 | 新worktreeの構成、用語、移植範囲、機能境界、新schemaを確定 | 状態所有者と新API、維持する挙動、移植する選択肢が説明できる |
| 2 | 新しい設定・選択肢・実体生成の仕組みと最小実行を用意 | 選択肢追加・削除、制約、実効設定保存を一つの実行経路で確認 |
| 3 | 予測・ラベル観測・診断を分離 | label観測前の予測、観測後更新、診断有無の同値性を確認 |
| 4 | 候補検証とデータ割当を分離 | 採否、FIFO帰属、割当変更、登録・統合の離散列が一致 |
| 5 | 学習と統合の責務・設定受渡しを整理 | optimizer更新・共有参照・通信/計算量・対象機能が一致 |
| 6 | 評価・保存・preset・掃引を仕上げ、旧構成を新ブランチから除く | 移植対象の挙動比較が通り、新実装が旧API・旧形式・旧実装へ依存しない |

各段階も一つの巨大commitにせず、一責務を抽出して検証できる単位へ分ける。
旧実装は固定した比較対象として使い、新しい機能は新実装側だけへ追加する。
新schema整合性、機能境界のテスト、移植対象に対応するgoldenの挙動比較をgateにする。
最終構成3ケースと移植するbaselineは必ず比較し、旧11ケース全ての方式を再実装することとは区別する。
変更箇所がgoldenのケース範囲外なら、対応する既存の期待挙動と同一条件の比較を追加する。

移行中は、乱数消費順、クライアント/expertの反復順、学習batch・optimizer更新順、
浮動小数点の集約順、共有モデルの参照関係、ID採番を維持する。
予測→ラベル観測→前向き検証確定→ClassESR更新→FIFO処理→学習→同期という
現在の時系列も維持する。疑わしい仕様や不具合は別に記録し、修正と同時に混ぜない。

新API・新形式への移行でテストの呼出し・key対応は変更してよいが、期待する数値・判断・処理順は維持する。
goldenの数値・離散的な挙動の変更を必要としないことを原則とする。
アルゴリズム変更が必要なら別の変更として理由・影響・再実験範囲を判断する。
環境と検証手順は[リファクタリング前の回帰基準](../experiments/refactoring-baseline.md)を使う。
保留の3資料と`results/`は維持する。

## 8. cc-sddの判断

**採用する価値がある。方針と境界を合意した後、新実装の設定・最小実行の一単位で限定的に導入することを推奨する。**
今回の作業は複数セッション・複数レイヤーにまたがるため、変更範囲・依存・不変条件・
検証証拠を保存できる仕組みが役立つ、という本プロジェクトへの判断である。

調査時の[公式README](https://github.com/gotalab/cc-sdd/blob/main/README.md)は、
Codex対応のSkills、要求・設計・taskの管理、タスクごとの実装・reviewを案内している。
[公式SDDガイド](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/spec-driven.md)では、
責務境界・依存・検証条件を明示し、architectureを仕様運用の前提と位置付けている。
導入によって責務分離が自動的に決まるものとは扱わない。

導入する場合の運用方針:

- 全体の規約は`AGENTS.md`、研究手法の説明は`docs/overview`と`docs/components`を正本とする。
- cc-sddのsteeringは正本を参照し、説明を丸ごと複製しない。
- 変更specには範囲、入出力、所有状態、依存、維持する処理順、移植範囲、新形式、検証を置く。
- 「全体リファクタリング」という一枚の巨大specにせず、まず設定・最小実行等の単位で試す。
- 最初は一taskずつ進め、goldenを含む既存検証を完了条件に組み込む。
- 新機能向けのfeature flagや同等テストの重複は、移動だけの作業に機械的に追加しない。
- ツールの版を固定し、生成される設定・指示が既存規約と衝突しないか確認する。
- taskの進捗は採用した仕組みに一本化し、別の仕様管理方式と二重管理しない。

2026-10-02に専用worktreeへcc-sdd 3.1.0（Codex Skills、日本語）を導入した。
最初のspecは`configuration-foundation`。要求と命名revision 2はユーザー承認済み。
設計と追加命名revision 4はgpt-6-lunaのレビューを反映し、2026-10-03に人間が承認した。最新状態は対象specの`spec.json`で確認する。
実装単位ごとに名前・役割・入出力・状態・単位を`naming.md`へ列挙し、
2026-10-03以降はgpt-6-lunaがレビューし、主担当が有用な指摘を反映した時点で命名承認とする。
これはユーザーの明示的な委任による。全指摘の採用は必須ではなく、採否と理由を保存する。
命名の追加・変更だけを理由に人間の承認を再要求しない。承認はrevision付きで保存する。
新実装のコードは命名承認前に作成しない。

## 9. セッション再開と合意の保持

2026-10-03の追加指示により、今後の要求・設計・task・命名・実装の承認は、gpt-6-lunaレビューと主担当による有用な指摘の反映で行う。不要と判断した指摘の採否と理由も保存する。各段階のレビューを省略せず、人間の承認を毎段階で再要求しない。承認対象・内容hash・証拠は対象specへ記録する。

- `AGENTS.md`から本方針、`.kiro/steering/roadmap.md`、対象specの`spec.json`・`review.md`・`naming.md`を読む。
- 本文書を全体方針の正本とし、steeringは要点と参照先を持つ。仕様と承認状態は対象specへ記録する。
- 人間の指示で方針が変わった場合は正本と関係するsteering・specを更新し、古い会話だけを判断根拠にしない。
- パッケージ名等の個別承認を、命名一覧全体・要求・設計・taskの承認へ広げない。

## 10. 旧実装の不具合・改善候補の追跡

調査・移植で発見した事項は[実装の不具合・改善事項](implementation-findings/README.md)へ一件一ファイルで記録する。個別記録が状態・再現条件・確認済み/未確認の影響・将来修正案の正本。対象specのresearch.mdからリンクし、今回の移植で維持した挙動を残す。
再現済みの不具合候補と、採否未定の改善案を分ける。修正後も記録を削除せずcommitと検証結果を追記する。記録だけで挙動変更やgolden更新を承認済みとは扱わない。詳しい項目・状態は入口READMEの規約に従う。
